    DvTP: the citizen views and revokes consents¶

    A logged-in citizen opens "Mijn toestemmingen" in the toestemmingsportaal. The portal shows the consents of the citizen with their status, and the citizen revokes one consent. The portal finds the consents through its own reference to the citizen, without a BSNk call. A revocation takes effect at the next request of the consumer.

    For the concepts, see Revocation and Citizen recognition: route D. For the components, see Level 2: consent chain. For the requirements, see Citizen access.

    Data per hop¶

    The tags are the data classes of What travels where. Each hop carries the following data:

    # From → to Endpoint In Out Data and notes
    1 Citizen → portal frontend (UI) DigiD mock login Portal token, sub = BSN The same as hops 3 to 5 of DvTP consent. In production, the identity comes from the MijnOverheid login (REQ-24, Q-50)
    2 Portal frontend → portal backend GET /portal/consents Portal token in Authorization — The BSN travels only inside the signed portal token. The citizen sends no reference and no BSN as a parameter (REQ-40)
    3 Portal backend (internal) — BSN subject_ref The portal computes an HMAC with its own secret, versioned key (route D). The portal does not call BSNk (TestListingAndRevokingDoNotCallBSNk)
    4 Portal backend → logbook LDV write dataverwerking.bsn-pseudonimisering under subject_ref, with attribute dpl.gbo.pseudonimiseringAanleiding = toestemmingen-inzien — The derivation is a separate processing (REQ-72, portal.go#L323-L340). The record holds no BSN
    5 Portal backend → register GET /consents?subject_ref={subject_ref} subject_ref — Medium. The register refuses a listing without subject_ref (TestAnUnscopedListingIsRefused). Only the network keeps other callers out (REQ-39, Q-58)
    6 Register → portal backend — — Records with consent_id, subject_ref, dienstverlener_oin, scopes, use_case, status, valid_until The records hold no BSN, no PI or PP, and no proof values (REQ-69, TestNoConsentAnswerCarriesThePolymorphicValues). The register logs dataverwerking.toestemming-inzage
    7 Portal backend → portal frontend — — Records plus effective_status The backend derives Revoked from the register status, Expired from valid_until, and otherwise Active (consent.go#L135-L146). The payload holds no BSN (REQ-20)
    8 Portal frontend → citizen (UI) — Overview The overview shows the statuses Actief, Verlopen, and Ingetrokken (REQ-38). The status Opgehaald is not built in demo v0.9.0 (Q-42, F-97). The overview has no export (REQ-108, Q-52)
    9 Citizen → portal frontend (UI) Revoke on consent_id — The UI shows the button only for an active consent (MijnToestemmingenDetail.tsx#L127)
    10 Portal frontend → portal backend DELETE /portal/consents/{id} consent_id, portal token — Revocation changes the status of the record. The register keeps the record
    11 Portal backend (internal) — BSN subject_ref As hop 3
    12 Portal backend → logbook LDV write As hop 4, with dpl.gbo.pseudonimiseringAanleiding = toestemming-intrekken — TestListAndRevokeLogTheirPseudonymisation
    13 Portal backend → register GET /consents/{id} consent_id — The backend reads the record to compare the owner. The register logs this read as dataverwerking.toestemming-inzage
    14 Register → portal backend — — Record with subject_ref —
    15 Portal backend (internal) Ownership check consent.subject_ref, subject_ref Allow or ErrNotOwned The check runs on the server side. The register cannot see who calls, so the portal backend does the check (portal.go#L268-L296)
    16 Portal backend → register DELETE /consents/{id} consent_id — The register sets REVOKED, keeps the record, and stores dataverwerking.toestemming-intrekken in the same transaction (main.go#L585-L596). It stores no revocation time (Q-48)
    17 Register → portal backend — — Record with status REVOKED —
    18 to 19 Portal backend → portal frontend → citizen — — {"status": "REVOKED"}, badge The answer holds no pointer to the rights of the citizen at the consumer (REQ-120)
    20 PDP → register Status lookup over FSC consent_id from the proof — Only at the next request of the consumer, as hops 10 to 12 of DvTP query. The consumer gets no message at revocation
    21 Register → PDP — — REVOKED The PDP does not cache the status, so the revocation takes effect at the next request (REQ-14)
    22 PDP (internal) Rules Resolved consent Deny Administrator code CONSENT_WITHDRAWN, consumer code FIELD_NOT_PERMITTED. Another active consent of the same citizen cannot replace the revoked one: the PDP checks only the consent_id from the proof

    Main observations¶

    The citizen-access flow in gbo-demo v0.9.0 has these properties and gaps:

    • The server derives the reference. The portal derives subject_ref from the BSN in the signed portal token. As a result, a citizen cannot list or revoke the consents of another citizen (REQ-40, TestListIsolatesByCitizen).
    • Viewing and revoking need no BSNk. The reference is an HMAC that the portal computes itself (route D, ADR-0040, proposed). A new key gives every citizen a new reference. Migration to a new key is not built (Q-56). It is open whether the register and the portal backend are one system (Q-49).
    • Revocation keeps the record. The status becomes REVOKED and the record stays. The effect reaches the consumer at its next request, through the online status lookup (REQ-14, DvTP query). The demo has no status cache, so the propagation time is one request. The norm for the propagation time is open (REQ-75, Q-47).
    • Every step is a logged processing. The portal logs each derivation of the reference with its reason. The register logs each read and the revocation under subject_ref. No record holds a BSN (TestNoBSNInAnyRecordedProcessing, Logging).
    • The demo does not meet all requirements. A revocation of the consent of another citizen gives 403, where REQ-40 asks for 404. The demo accepts a second revocation (REQ-109). The demo has no export (REQ-108), no rights notice (REQ-120), no "retrieved" status (Q-42), and no revocation time (Q-48).
    • The register trusts its caller. The register serves list, read, and revoke to every caller on its network. Only network placement limits this to the portal backend (REQ-39, Q-58).
