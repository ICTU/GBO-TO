    Pseudonymization¶

    Private consumers must not process the BSN (P-04). In DvTP, they still request data about one citizen from government sources. For this, GBO uses the BSNk PP polymorphic pseudonym scheme. GBO calls BSNk only at consent time (ADR-0005). In the consent route, the consumer holds no identifier of the citizen: no BSN and no pseudonym (REQ-20). After the PDP allows the request, only the source turns its own value back into the BSN (ADR-0033).

    Pseudonymization realizes capability S03. For the BSNk rules that shape this design, see BSNk preconditions. For the consent proof that carries the values, see Consent.

    Identifiers¶

    Each identifier of the citizen or the consent has its own maker and holder:

    Identifier What it is Made by Held by
    BSN The citizen service number DigiD login, or PID disclosure (EUDI, ASI) The portal backend during the login. The source, inside its own boundary
    PI, PP Polymorphic identity and polymorphic pseudonym. Only the requester can get them transformed (BSNK-03) BSNk Activate, once per citizen The portal backend. The register stores them under subject_ref (REQ-69)
    VI (encrypted identity) A value for one recipient OIN and key version. It decrypts to the BSN. It exists only for a recipient on the BSN authorization list (BSNK-06) BSNk Transform, at consent Inside the consent proof, encrypted_subject[<OIN>].identity
    VP (encrypted pseudonym) A value for one recipient OIN and key version. It decrypts to the own pseudonym of that recipient for the citizen. Every recipient gets one BSNk Transform, at consent Inside the consent proof, encrypted_subject[<OIN>].pseudonym
    Placeholder consent:identity or consent:pseudonym: the name of the subject in a consent-based query Fixed values (lib.rego#L43-L53) The consumer query and the PDP input. The source gateway replaces it
    subject_ref HMAC of the BSN with the secret, versioned key of the portal Portal backend (subjectref.go#L38-L42) Portal backend and register: the key to the consents of the citizen
    consent_id The consent record Consent register (toestemmingsregister) Consumer: its only handle on "this person"

    PI and PP belong to the portal. VI and VP belong to their recipient. No other party can read them. In the demo, every party can read them because the mock does not encrypt. For more information, see Demo mock and production BSNk.

    Values made at consent time¶

    BSNk transforms values only while the citizen is logged in (BSNK-04). A query comes later. As a result, the portal makes every value that a source needs while the citizen gives consent (portal.go#L119-L192). The portal does these steps:

    1. It derives subject_ref from the BSN.
    2. It looks up PI and PP under subject_ref in the register. At the first consent of this citizen, it activates the BSN once at BSNk and stores PI and PP (portal.go#L296-L314).
    3. It reads the BSN authorization list from a copy. The copy is at most BSN_AUTHORISATION_LIST_MAX_AGE old (default 1 hour).
    4. It transforms PP to a VP for every source. It transforms PI to a VI for every source on the list (portal.go#L197-L224). Each BSNk request names at most four parties (BSNK-05, bsnk.go#L102-L115).
    5. It sends the values to the register. The register signs them into the proof and does not store them.

    For each source, the portal must know the OIN, the key version, and the BSN authorization (REQ-82). In the demo, this is configuration: CONSENT_SOURCES=<OIN>@<key set version> (docker-compose.yml#L1005). If no source is configured, the portal gives no consent. A service catalogue that carries these facts is not built (#382).

    The portal makes all values at consent, so the proof freezes. For more information, see Consent (F-78).

    Citizen recognition: route D¶

    To show and revoke the consents of a citizen without a BSN, the consent facility (toestemmingsvoorziening) needs a stable key. A stored PI or PP is not a stable key, because BSNk gives other values at every activation. The proposed solution is route D (ADR-0040, proposed, route D). Route D works as follows:

    • The service recognizes the citizen by an HMAC of the BSN, with a secret, versioned key. Every record keeps the key version.
    • The service activates once and stores PI and PP under that reference.
    • To show or revoke consents, the service does not call BSNk.

    The register stores PI and PP, but no BSN and no per-party value (REQ-69, REQ-23). This is an intentional deviation from FR-35, criterion 1 (F-98). For the other routes, see BSNk preconditions.

    Route D has these open points:

    • Are the register and the portal backend one BSNk participant (Q-49)? In the demo, the backend activates and the register stores.
    • A changed HMAC key gives every citizen a different reference. Then the service does not show older consents. Migration is not built (Q-56).
    • The protection of the stored PI and PP is open (Q-57). Retention is also open (Q-63).

    Where the boundary is enforced¶

    The BSN is in three places only. All three places are inside the government:

    1. Portal backend, at login: the backend derives subject_ref. At the first consent, it sends the BSN to BSNk. After that step, no component holds a BSN, because the draft consent has no field for one (portal.go#L116-L118). It is open how the backend inside MijnOverheid gets the verified identity (Q-50).
    2. BSNk, at activation: BSNk records every activation in its inspection register, the Inzageregister (BSNK-10).
    3. The source, after the allow: the source gateway takes the value for its own OIN from the proof. The decryption component of the source reads the value with the keys of the source. The gateway accepts the result only if the value names the OIN of the source as recipient (substitution.go#L213-L251, REQ-80). Then the gateway replaces the placeholder. BSNk is not in the query path (REQ-21).

    The register never gets a BSN, not even for a short time (REQ-23). The consumer never gets a BSN in the proof or in the response.

    Like the PDP, the gateway acts on the evidence. If the request carries a consent token, the gateway takes the subject from the token. If the request has no consent token, the gateway passes it through unchanged (PID regime). The gateway reads no grant property. The value for the requested form can be missing, for example no VI for a source that is not on the list. In that case, the gateway does not forward the request.

    Network isolation is the control¶

    The gateway does not verify the proof again (substitution.go#L105-L107). A second check adds nothing, because a consumer holds real proofs. The rule "after the decision" holds only while the Inway is the only component that reaches the gateway (REQ-81, F-79).

    In the demo, the gateways publish no port. They are on two networks only:

    • source-gateways, shared with the source Inways.
    • sources, shared with the source services, the decryption component, and the logbooks (docker-compose.yml#L829-L836).

    No consumer is on either network. Outside Docker Compose, this isolation needs a Kubernetes NetworkPolicy or an equivalent control. The Helm chart in demo v0.9.0 has no NetworkPolicy. A nonce that binds a value to one consent, as a second line, is not built. For the zones, see Deployment.

    Subject binding¶

    Under a consent, the PDP does not compare identifiers. The query names the subject with a placeholder. The source can fill in only the subject from the proof (REQ-79, F-77). For the rule, see Authorization. Subject binding has these consequences:

    • No policy at the PDP can depend on who the citizen is.
    • One request names one subject. A question about two persons does not fit. This needs a design decision.
    • Substitution works only on variables. If the query text holds a literal placeholder, the placeholder passes the PDP. The gateway does not replace it, and the query finds nobody.
    • The PDP input and the decision logs have no identifier. They do hold the proof with the encrypted values.

    The consumer has no identifier¶

    The consumer reads only consent_id and scopes from the proof (F-76). This goes further than the "BSN-free" rule of P-04, because the consumer is free of all identifiers. This has three effects:

    • Logging: the consumer logbook names the data subject by the consent ID, with subject type consent-id (logbook.go#L20-L22). In the logbook, one citizen with two consents is two data subjects. It is open whether this fits LDV (Q-27).
    • Access requests: a citizen can ask the consumer what it processed. The consumer can find the citizen only through the consents of the citizen.
    • Recognition: through GBO, the consumer cannot tell that two consents are from the same person. This is data minimization, and a design choice.

    With its own VP, the consumer has a pseudonym to log under. This option is in the design and not built (#478, Q-01). A source API that answers on a pseudonym is also not built. No demo rule accepts consent:pseudonym (#474).

    Exception: the BSN in the EUDI and ASI routes¶

    The EUDI adapter and the ASIP put the plain BSN from the PID or the token into the query variables. As a result, the BSN is in the PDP input and in both decision logs: the ADL and the console log (source_metadata.go#L273, source.go#L94). The PDP does not call BSNk. This is a known violation of REQ-60. The demo accepts it until #368 decides between masking and "transform first" (CHANGELOG).

    The proposed decision keeps identifiers out of the PDP input and uses masking only as a second line (ADR-0043, proposed). Earlier, masking in the policy engine had no effect (F-54). LDV records never hold a BSN, because the logbook refuses one (Logging).

    Demo mock and production BSNk¶

    The demo uses bsnk-mock (README). The mock follows the BSNk interface (/v2/activate, /v2/transform, /v2/bsn-authorisation-list, and more), but as JSON instead of SOAP. The mock enforces these rules:

    • Only the requester can use the PI.
    • The BSN authorization list applies.
    • A request names at most four parties.
    • The mock reads values per key version.

    The mock and production BSNk differ in these properties:

    Property Demo Production
    Encryption None: any party that holds a PI or VI can read the BSN Encrypted values, unlinkable between parties
    Values Stable by default. Random with RANDOMIZE_VALUES=true, as real BSNk Different at every request
    Interface JSON over HTTP SOAP with PKIoverheid (BSNK-11)
    Who can activate Not checked: the mock takes the requester from the request Only a recognized participant (BSNK-01, F-75, Q-26)
    Activation input The BSN. The mock does not check it against a population register The BSN and check data (BSNK-02)
    Recipient keys Demo keys in the gateway image Per recipient through an Access Service or Key Requester (BSNK-09, #467)
    Key versions The mock accepts any key set version A value belongs to one key version. The source keeps older keys while proofs for them are valid (BSNK-08, AV-09)
    Decryption component One, shared by the three demo sources, which also share one OIN One per source, each with its own OIN (BSNK-07)

    The same image, started with DECRYPTION_COMPONENT_ONLY=true, is the decryption component of the sources (docker-compose.yml#L773-L786). The mock does not encrypt and the sources share one OIN. As a result, the demo does not show unlinkability between parties. For the certificates and keys per party at onboarding, see BSNk preconditions.
