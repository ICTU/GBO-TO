    EUDI wallet channel¶

    In the EUDI wallet channel, a citizen gets data from a government source in the EUDI wallet. Interaction pattern A of the Globaal Ontwerp has two flows. In flow A, the source issues an attestation itself, as a PubEAA. In flow B, a QTSP verifies or retrieves the data at the source and issues a QEAA. GBO delivers one component for each flow, and both components reach the source through GBO Basis.

    The channel has these parts:

    Part Role Zoom in
    PubEAA provider The technical issuance facility. The issuance server asks the wallet for the PID. The EUDI adapter gets the source data and turns it into claims. The bronhouder stays the PuB-EAA provider (ADR-0028, proposed). PubEAA provider
    ASI provider Lets a QTSP verify or retrieve attributes at the source (eIDAS article 45e). It has its own OAuth authorization server. The QTSP is an OAuth client there, and not an FSC participant (F-87). ASI provider
    Source registry Holds the active release of every source description. The source describes its attestations (eudi) and its attributes (asi) itself. Source onboarding
    GBO Basis Decides every request of the channel under the PID regime, with the rules EUD0001, EUD0002 and ASI0001. GBO Basis
    NL Wallet and QTSP External parties. The wallet holds the PID of the citizen. The demo runs a reference QTSP, which is not a real QTSP. ASI verification

    Flow A: the source issues a PubEAA¶

    In flow A, the citizen shares the PID with the issuance facility and gets an attestation back. The attestation carries the name of the source as the issuer:

    sequenceDiagram autonumber actor B as Citizen box rgb(241,239,232) External participant W as NL Wallet end box rgb(255,237,213) PubEAA provider participant IS as Issuance server participant AD as EUDI adapter end box rgb(220,252,231) GBO Basis at the source participant PDP as PEP + PDP end box rgb(221,235,247) Source participant S as Source API end B->>W: scan the QR code of an offer W->>IS: fetch the request IS-->>W: ask for the PID claim bsn, in the name of the source B->>W: share the PID W->>IS: PID as SD-JWT VC Note over IS: check the PID<br/>against the trust anchors IS->>AD: callback with the disclosed PID Note over AD: BSN from the PID,<br/>query from the release AD->>PDP: query with the BSN, over FSC Note over PDP: no consent token,<br/>so PID regime, EUD0001 PDP->>S: allow, query through the gateway S-->>AD: source data Note over AD: claims with gbo-simple-v1 AD-->>IS: claims and type IS-->>W: attestation, signed for the source W-->>B: accept the attestation

    Figure 2: Flow A, at essence level. The runtime page has every hop.

    The facility signs with the certificate set of the source. The wallet shows the source as the issuer. GBO plays no part when the citizen later presents the attestation to a dienstverlener. For every hop, with the data and the error paths, see EUDI issuance.

    Flow B: a QTSP verifies at the source¶

    In flow B, the QTSP asks the ASI provider to verify or retrieve attributes at the source. The citizen approves the request by logging in at the authorization server:

    sequenceDiagram autonumber actor B as Citizen box rgb(241,239,232) External participant Q as QTSP participant W as NL Wallet end box rgb(255,237,213) ASI provider participant AS as Authorization server participant ASIP as ASIP end box rgb(220,252,231) GBO Basis at the source participant PDP as PEP + PDP end box rgb(221,235,247) Source participant S as BRP end B->>Q: ask for a statement Q-->>B: redirect to the authorization server B->>AS: see who asks what at which source W->>AS: log in with the PID (or the DigiD mock) AS-->>Q: code, then a token with the BSN Q->>ASIP: verify or retrieve, with the token Note over ASIP: check the token,<br/>BSN from the token ASIP->>PDP: query with the BSN, over FSC Note over PDP: PID regime, ASI0001 PDP->>S: allow, query through the gateway S-->>ASIP: fields of the person ASIP-->>Q: sealed result per attribute Q->>W: test statement, not a QEAA

    Figure 3: Flow B, at essence level. Discovery and registration of the QTSP happen once, before the first request.

    A token is valid for one data service, and each data service serves one source. The QTSP issues the QEAA itself. In the demo, the reference QTSP issues a test statement through the issuance server of flow A. For every hop, see ASI verification.

    Who sees which identifier¶

    The channel does not use BSNk. The BSN goes into the source query as a plain value:

    In flow A, the EUDI adapter takes the BSN from the disclosed PID. In flow B, the ASIP takes it from the access token. Both components put the BSN in the query variables. As a result, the BSN is in two kinds of places that do not need it:

    • The PDP input, and with it the ADL and the console decision log. This is a known violation of REQ-60. The proposed fix keeps identifiers out of the PDP input (ADR-0043, proposed).
    • The access token of flow B. ETSI requires the identification data in the token, and the QTSP can read the BSN (F-86).

    The LDV records hold no BSN, because the logbook refuses one. For the detail, see Exception: the BSN in the EUDI and ASI routes.

    The PID regime¶

    Neither flow carries a consent proof. The evidence in the request selects the regime, so both flows land in the PID regime (ADR-0031):

    Each PID rule admits only named callers: the FSC peer of the EUDI adapter, or the ASIP peer. Only consent is positive evidence. A request enters the PID regime because it carries no token (F-70). For that reason, the actor lists of the PID rules must stay disjoint from the consent consumers. The fix in the design is a verified PID disclosure, bound to the subject of the query (REQ-45).

    In demo v0.9.0, the callback that carries the PID is not authenticated. The callback gap shows what that allows.

    Approval in the wallet is no legal basis¶

    In flow A, the citizen chooses in the wallet to share the PID. In flow B, the citizen approves one request by logging in (REQ-90). The ARF says that approval in the wallet is never a legal basis for the relying party (F-83). The approval of flow B is also not stored, and the citizen cannot revoke it. A DvTP consent and a wallet approval cannot replace each other. For the detail, see Wallet approval is not a legal basis.

    Compared with the Globaal Ontwerp¶

    The demo follows the two flows of pattern A. It differs in six steps:

    Step Globaal Ontwerp Demo v0.9.0
    Start of flow A The wallet sends a credential request to the PubEAA voorziening. The citizen scans a QR code. The issuance server first asks for the PID (disclosure-based issuance, ADR-0018).
    Authorization in flow A An Autorisatievoorziening asks the wallet for the PID and authorizes the PubEAA voorziening. No separate service. The nl-wallet issuance server checks the PID and calls the adapter. The adapter does not authenticate that call.
    Authorization in flow B The verify and retrieve service uses the same Autorisatievoorziening of GBO. The ASI provider has its own OAuth authorization server, with a wallet verifier and a DigiD mock (ADR-0037).
    Approval by the citizen The wallet shows the request and asks for consent. Flow A: the citizen shares the PID. Flow B: the citizen logs in. Neither is a stored consent.
    Format of the attestation SD-JWT VC or mdoc SD-JWT VC (dc+sd-jwt) only
    Result of flow B The QTSP issues a QEAA. The reference QTSP issues a test statement, marked as not qualified.

    The GO also says that a request over ISO 15000 needs no authorization. The demo offers clause 6.1 of ETSI TS 119 478 only (REQ-112). In both the GO and the demo, GBO itself is not a PubEAA provider.

    Open points¶

    The main open points in the EUDI wallet channel are these:

    • Nothing binds the BSN in the source query of flow A to a checked PID disclosure (REQ-45, Q-18).
    • The BSN is in the PDP input and in both decision logs (F-54).
    • The QTSP can read the BSN in the access token (F-86).
    • Nothing links the citizen who logs in at the QTSP to the citizen who logs in at the authorization server (F-93).
    • The regulatory frame for PuB-EAA issuance and the designation of the issuer (F-81, Q-28).
