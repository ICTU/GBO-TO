    PubEAA provider¶

    The PubEAA provider issues an attestation with source data to the EUDI wallet of the citizen. It is flow A of interaction pattern A in the Globaal Ontwerp. GBO operates the technical issuance facility, and each bronhouder stays the PuB-EAA provider of its own attestations (ADR-0028, proposed). The facility runs on the nl-wallet issuance server (ADR-0018). The EUDI issuance runtime page has every hop and the links to the code.

    Each component has one job:

    Component Job Never does
    Issuance server Asks the wallet for the PID over OpenID4VP and checks it against its PID trust anchors. Issues the attestation over OpenID4VCI, signed with the issuer certificate of the source. Calls the source
    EUDI adapter Takes the BSN from the PID. Builds the query from the active release and calls the source through its own FSC Outway. Turns the answer into claims and writes two LDV records. Keeps source data, or has a query or mapping of its own (REQ-44)
    Release runtime Polls the active release and rebuilds the bindings of the adapter. If an error occurs, it keeps the previous snapshot. Fetches source metadata itself
    Source reconciler and registry The reconciler fetches and validates the source document. Promotion writes an immutable release and sets the active pointer. Activates a source because of a valid FSC contract (REQ-65)
    Certificate set Issuer, reader and status-list certificates of one source. The wallet shows the issuer and the purpose from these certificates. Serves another source (REQ-58)
    Issuance init Writes the configuration of the issuance server from the active release. The server reads it only at startup, so a new release needs a controlled restart. —

    The issuance flow¶

    One issuance of the income declaration for 2024 takes these steps:

    sequenceDiagram autonumber actor B as Citizen box rgb(241,239,232) Wallet and demo portal participant P as Developer portal participant W as NL Wallet end box rgb(255,237,213) PubEAA provider participant IS as Issuance server participant AD as EUDI adapter end box rgb(237,233,254) Records participant LB as Adapter logbook end box rgb(220,252,231) GBO Basis at the source participant PDP as PEP + PDP participant GW as Source gateway end box rgb(221,235,247) Source participant S as Source API end P->>AD: GET /eudi-offers.json AD-->>P: offers of the active release B->>W: scan the QR code of an offer W->>IS: fetch the disclosure request IS-->>W: ask for the PID claim bsn, with the reader certificate of the source W->>IS: PID as SD-JWT VC, after the citizen approves Note over IS: check the PID against<br/>issuer_trust_anchors IS->>AD: POST /attestations/belastingdienst/inkomensverklaring?jaar=2024 Note over AD: type in the release, BSN from<br/>the PID, parameters in an offer AD->>LB: record pid-bsn-extractie AD->>PDP: query with the BSN, over FSC Note over PDP: PID regime, EUD0001 PDP->>GW: allow GW->>S: query, unchanged S-->>AD: income data, back through FSC Note over AD: claims with gbo-simple-v1 AD->>LB: record attestatie-samenstellen AD-->>IS: claims, VCT, format dc+sd-jwt IS-->>W: attestation over OpenID4VCI W-->>B: accept the attestation

    Figure 2: One issuance, at essence level.

    Three properties of this flow matter for the design:

    • The issuance server checks the PID. The adapter trusts the callback without a check of the caller (The callback gap).
    • The adapter writes an LDV record before it calls the source. If the logbook does not acknowledge the record, the adapter does not call the source. Neither record holds the BSN (REQ-72).
    • The offer and the policy are separate limits. The source offers 2024 and 2025, and EUD0001 allows the same years. Publication by the source does not authorize the data (F-74).

    For every hop, with the data and the code, see EUDI issuance.

    A claim has a pointer into the answer, a datatype, a label and a setting for selective disclosure. GBO derives the projection from the claims. It also generates the SD-JWT VC Type Metadata from display and claims (ADR-0017, REQ-64). As a result, the schema in the Type Metadata always matches what the projection fills.

    The URL of the Type Metadata is the VCT of the type version. A change to the claims or the display changes the bytes behind that URL, so the change needs a new type_version. The profile gbo-simple-v1 allows only scalar claims. Nested claims are not built (REQ-78).

    The demo has two attestation types:

    Type Source and service Rule Offers Subject of the data
    Inkomensverklaring Belastingdienst, bri EUD0001 jaar 2024 and 2025 The PID holder
    Akte van overlijden RvIG, brp EUD0002 One, without parameters The deceased partner of the PID holder

    Figure 4: The checks of the adapter, in order. Red: the HTTP status that the issuance server gets.

    The issuance server gets only the HTTP status. The reason is in the adapter log (stage), and for a PDP deny also in the ADL. The FSC Inway removes the reason of a deny on the way back. These rules hold for every error path:

    • No attestation reaches the wallet, and a partial attestation does not exist (REQ-116).
    • A PDP deny (ACTOR_NOT_ALLOWED, PID_NOT_PRESENT, YEAR_NOT_ALLOWED, FIELD_NOT_PERMITTED) gives 502, the same status as a chain that does not answer.
    • If the logbook does not acknowledge an LDV record, the adapter answers 500 and does not continue.
    • A missing or incomplete certificate set blocks only that source (REQ-58).

    The offer list is an exception to the isolation per source. If one source is past its grace period, /eudi-offers.json answers 503 for every source (#606). For all triggers, see Error paths.

    The callback gap¶

    The issuance server checks the PID. The adapter does not know that a callback comes from the issuance server:

    Figure 5: The callback gap. Dashed: the two fixes that REQ-45 names. Demo v0.9.0 builds neither.

    No mechanism binds the BSN in the callback to a checked disclosure (REQ-45, Q-18, #133). The PDP sees the designated issuer peer and a BSN, so it allows. The list of designated issuers is the only gate of the PID regime (F-70). The demo uses the gap itself: a playground in the developer portal posts a typed BSN to the adapter.

    The demo dropped a PID check in the adapter, because the issuance server checks the signature (SL-25). The PID trust list of the issuance server is also too broad. Next to the PID provider, it trusts the GBO development CA and the issuer CA of every source. Both fixes of REQ-45 need a binding of the disclosure to the request.

    The source selects the marriage that ended by the death of the partner. If the partner died on another date than the dissolution, the source returns nothing, and the adapter answers 404. The PDP does not see the relation. The deceased is not a data subject under the GDPR, so the source logs the requester and the living parents (AV-10).

    The preferred design puts the relation in filter arguments of the published schema. The policy then requires these arguments with fixed values (#425, Q-14). In demo v0.9.0, a caller can ask for the akte of any BSN, because of the callback gap.

    Figure 7: Trust roles in PuB-EAA issuance. Dashed: not built or not decided.

    ADR-0028 (proposed) divides the roles. The bronhouder is the PuB-EAA provider and stays legally responsible for content, validity and revocation. GBO operates the technical issuance facility and is probably the EEAIssuer in the notification of each bronhouder. The facility is optional: a bronhouder can run its own credential issuer.

    Since August 2026, PuB-EAA issuance falls under the same standard as QEAA issuance (F-81). That frame asks for these parts:

    • Designation of the issuer.
    • A registration certificate.
    • A qualified seal in a QSCD.
    • Conformity with ETSI TS 119 471 and TS 119 472-3.

    Demo v0.9.0 is not checked against this frame. One development CA fills all roles. Three decisions are open: who designates the issuer (Q-28), on which trust list the providers appear (Q-30), and who holds the keys (Q-17). For the certificate roles, see EUDI trust roles.

    Compared with the Globaal Ontwerp¶

    The demo follows flow A of pattern A. It differs in three points:

    Point Globaal Ontwerp Demo v0.9.0
    Role of GBO A technical, central and optional facility. GBO is not a PubEAA provider. The same. The bronhouder is the provider (ADR-0028, proposed).
    Authorization An Autorisatievoorziening authorizes the PubEAA voorziening after a PID login. The issuance server checks the PID itself. No separate authorization service exists.
    Semantic mapping A shared GBO facility translates the format of the source. The source maps its own fields to claims with gbo-simple-v1. No translation layer exists.

    Open points¶

    The main open points in the PubEAA provider are these:

    • The callback gap: nothing binds the disclosure to the source query (REQ-45, Q-18).
    • The regulatory frame for PuB-EAA issuance, and who designates the issuer (F-81, Q-28).
    • The trust list for PuB-EAA providers (Q-30).
    • Every attestation is valid for 365 days. GBO gets no change signal from the source, so it cannot revoke on a change (F-82, REQ-77).
    • The source description does not mark the relation behind a related-person attestation (F-47).
