    GBO Basis¶

    GBO Basis opens a government source in one standard way, for every channel. It runs at the bronhouder: each source has its own FSC Inway, its own PDP and its own source gateway. No central server decides for all sources (ADR-0004). GBO delivers the components, and the bronhouder runs them (P-10).

    The request path¶

    A request through GBO Basis has the same steps in every channel. The PDP decides before anything reaches the source. The source gateway does its work only after an allow:

    sequenceDiagram autonumber box rgb(241,239,232) Channel participant C as Caller end box rgb(220,252,231) GBO Basis at the bronhouder participant IN as FSC Inway (PEP) participant PDP as PDP participant GW as Source gateway end box rgb(221,235,247) Source participant API as Source API end box rgb(237,233,254) Records participant R as ADL, LDV end C->>IN: GraphQL query over FSC (mTLS, token) IN->>PDP: AuthZEN question with the raw body Note over PDP: field list, regime,<br/>rules per field PDP->>R: decision record (ADL) PDP-->>IN: allow or deny alt deny IN-->>C: deny, nothing reaches the source else allow IN->>GW: the judged request opt consent proof present Note over GW: decrypt own value,<br/>replace the placeholder end GW->>API: query API->>R: processing record (LDV) API-->>C: only the selected fields end

    Figure 2: One request through GBO Basis.

    The steps work as follows:

    1. The caller sends a GraphQL query through its FSC Outway. The Inway checks the certificate and the contract of the caller.
    2. The Inway sends the request, with its raw body, to the PDP as an AuthZEN question. The Inway does not read the query (REQ-42).
    3. The PDP turns the query into a list of fields, selects the regime from the evidence, and decides each field. Authorization shows how.
    4. The PDP writes the decision to the ADL, the audit record of decisions (ADR-0036).
    5. On a deny, the source sees nothing. By design, the caller gets a coarse reason code. The FSC Inway of demo v0.9.0 drops that code on the way back.
    6. On an allow, the Inway passes the request to the source gateway. Only the Inway can reach the gateway (ADR-0033).
    7. Under consent, the gateway decrypts the value that the consent proof holds for this source. It puts the BSN or the source pseudonym in the place of the placeholder. Without a consent proof, it passes the query unchanged.
    8. The source runs the query and returns only the selected fields (REQ-08). It logs the processing in its own LDV logbook.

    The PEP, the PDP, policy management and source access are decentral, at the bronhouder. The toestemmingsvoorziening is central and mandatory for DvTP (Q-10, ADR-0021). The PSA has not decided who operates the central facilities (open decisions B-06 and B-17). The demo runs everything in one stack and shares one PDP between the sources. That is a demo shortcut.

    Open points¶

    The main open points in GBO Basis are these:

    • The PID regime has no positive evidence of its own. A request without a consent proof enters it (F-70).
    • The rule "only after the decision" depends on the network. Only the Inway can be allowed to reach the source gateway (F-79).
    • The ADL record holds only what the consumer also sees (F-72).
    • A broken policy module stops every decision, without a visible fallback (F-52).
