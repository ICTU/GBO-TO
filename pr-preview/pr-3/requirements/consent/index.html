    Consent requirements (DvTP)¶

    These requirements cover the consent of the citizen in the DvTP channel. They cover the consent proof and its lifecycle, and the start of a request. They also cover the roles of portal and register, access and revocation by the citizen, and the data model of the register. For the design, see Toestemmingsvoorziening.

    This page has the following parts:

    • Consent proof and use
    • Consent lifecycle requirements
    • Consent initiation and return requirements
    • Role split between consent register and consent portal (S01/S02)

    Consent proof and use¶

    In the DvTP route (Data via Third Parties), a citizen gives consent to a private dienstverlener to get data about the citizen from a source. The requirements on this page cover three topics:

    • what a consent covers
    • what the citizen sees and confirms
    • how the authorization chain checks a consent at every request

    The toestemmingsportaal is the portal UI inside MijnOverheid plus the consent portal backend. It records the choice of the citizen. The toestemmingsregister stores the consent and issues a signed consent proof. The consumer sends that proof with each request. The PDP of the source checks the proof itself, and asks the register for the current status over FSC (ADR 0032). If an integrator connects, the consent binds the represented party (ADR 0034).

    The related topic pages are consent lifecycle, consent register data model, role split S01/S02, initiation and return, citizen access and revocation, and pseudonymization.

    Evidence links to gbo-demo point at tag v0.9.0. The linked files did not change between the review commit 819f3eb and v0.9.0.

    REQ-10: Consent covers a whole data set, and the citizen does not pick fields within a set¶

    A consent MUST apply to one or more indivisible data sets (scopes). It MUST NOT apply to separate fields. The citizen MUST NOT be able to exclude fields within a set.

    Under a consent for a set, the PDP MUST allow exactly the fields that the service fixes for that set. The PDP MUST NOT allow more fields. The PDP MUST NOT allow only a part of them because of a field choice in the consent. If a request asks fields of a set without consent, the PDP MUST deny it.

    Case Outcome
    Consent for the set, and the request asks fields of that set allowed (code)
    The request also asks a field that is not part of the set that field denied: NO_APPLICABLE_RULE (code)
    Consent only for another set denied: SCOPE_NOT_ALLOWED, or YEAR_NOT_COVERED for another tax year (code)
    The citizen switches a set off no consent for that set. The citizen cannot switch off a part of a set (code)

    REQ-12: A consent is bound to one consumer, one service, and a named data scope¶

    Every consent MUST be bound to one consumer (OIN), one service with its purpose, and at least one named data set. The portal MUST NOT offer consent for a request without a purpose or a data set. The toestemmingsregister MUST NOT record a consent without a consumer, a service, or a data set. If a consent has no data set or no purpose, the consent portal backend MUST refuse it with CONSENT_SCOPE_MISSING. The UI then offers no button.

    Case Outcome
    Consumer, purpose, and at least one known set recorded (code)
    No consumer not recorded. The register refuses (code: HTTP 400 dienstverlener_oin is required)
    No set chosen button disabled. The backend refuses: CONSENT_SCOPE_MISSING (not built in the backend in demo v0.9.0)
    No purpose refused: CONSENT_SCOPE_MISSING (the demo fills in hypotheek, which deviates)
    A set that the portal does not know no consent question. The citizen sees "Onbekend verzoek" (code)

    REQ-14: After revocation, the chain denies every later request on that consent¶

    After the citizen revoked a consent, the authorization chain MUST deny every later request on that consent. This also applies to a proof that was valid before the revocation. The deny MUST work without any action by the consumer and without a message to the consumer.

    Case Outcome
    Consent revoked, and a request with the proof denied: CONSENT_WITHDRAWN (code)
    The same proof before and after the revocation first allowed, then denied. The proof itself does not change (code)

    REQ-68: The PDP decides only on a consent whose origin, binding, and current status it establishes itself¶

    The consent proof of a request MUST bind at least these items: the citizen, the granted sets, the consumer, the authorization service, and the validity. The proof MUST bind the citizen as a value per receiving party (REQ-80). The consumer is the party to whom the citizen gave the consent. The authorization service is the service for which the proof is meant.

    Before it allows, the PDP MUST establish itself that the register issued the proof, and that the proof is unchanged. It MUST establish that the binding is complete. It MUST establish that the consumer is the party on whose behalf the request is made. It MUST also establish the current status of the consent.

    If the PDP cannot establish one of these points, it MUST deny. The sets, the citizen, and the consumer on which the PDP decides MUST come from that established proof.

    Case Outcome
    Valid proof, consent active, consumer matches allowed (code)
    Signature does not verify, unknown key, or another algorithm denied: CONSENT_SIGNATURE_INVALID (code)
    The PDP cannot get the verification keys denied: CONSENT_KEYS_UNAVAILABLE. The consumer sees ACCESS_DENIED (code)
    Another issuer, another audience, another type, or a mandatory claim is missing denied: CONSENT_CONTEXT_INVALID (code)
    Consent given to another consumer denied: CONSENT_ACTOR_MISMATCH (code)
    The register does not know the consent denied: CONSENT_NOT_FOUND (code)
    The PDP cannot establish the status (time-out, error, unexpected answer) denied: CONSENT_STATUS_UNAVAILABLE. The consumer sees ACCESS_DENIED (code)

    REQ-75: Consent status is available within a set propagation time, availability, and latency¶

    The toestemmingsregister MUST deliver the current status of a consent within a set maximum propagation time. The propagation time runs from the revocation by the citizen to the first deny in the chain. The register MUST also meet a set availability and a set latency per query. If the status cannot be established in time, the chain MUST deny (REQ-68). The mechanism (query per request, status list, or push) MAY be chosen freely, as long as it meets the set values. If a mechanism has a propagation time of more than zero, it MUST record that time.

    REQ-76: The register gives consent status only to an authenticated, authorized PDP, over FSC, and records who asked¶

    The toestemmingsregister MUST give the status of a consent only to an authenticated, authorized component. That component is the PDP of a source that offers the service for which the consent applies. The query MUST go over FSC.

    The register MUST record the verified identity of the caller in its processing log (REQ-72). Along the same path, only the status of the register MUST be reachable.

    Case Outcome
    PDP peer with a contract asks the status status delivered. The peer is the processor in the LDV record (code)
    Query without an FSC peer denied: HTTP 401 (code)
    Another path than the status through the status service (detail, list, revoke) denied (code)
    Peer with a contract, but not the PDP of a source of that service denied. Not built in demo v0.9.0: the demo delivers the status (code)

    REQ-106: An integrator acts only with a registered mandate, and the consent binds the represented party¶

    If an integrator calls on behalf of a dienstverlener, the authorization decision MUST check the consent against the represented party. It MUST NOT check the consent against the party that makes the connection.

    The connecting party MUST have a registered mandate for that dienstverlener and that use. If there is no mandate, the request MUST be denied. A mandate MUST have a validity. Outside that validity, a request MUST be denied as if there is no mandate.

    A contract in which a party connects on behalf of another party MAY come into force only if that representation is registered.

    Case Outcome
    Consent for dienstverlener X, and integrator registered for X and this rule allowed
    Consent given to another dienstverlener denied: CONSENT_ACTOR_MISMATCH
    Integrator registered only for another rule denied: INTEGRATOR_NOT_REGISTERED
    Integrator suspended denied: INTEGRATOR_NOT_REGISTERED
    Mandate not in force at that time, or expired denied: INTEGRATOR_NOT_REGISTERED (proposal: not built)
    The admission register delivers no data denied: INTEGRATOR_REGISTER_UNAVAILABLE
    Consent given to the integrator itself instead of the dienstverlener denied: CONSENT_ACTOR_MISMATCH
    No registration of the representation contract stays proposed: DELEGATION_NOT_REGISTERED
    Dienstverlener suspended, for a delegated contract contract stays proposed: PARTY_NOT_ACTIVE
    The dienstverlener calls itself, with or without an integrator in the chain allowed, unchanged

    REQ-107: Consent can be given only after confirmation that the citizen saw the information¶

    The UI of the toestemmingsportaal MUST make the action "give consent" available only after the citizen confirmed that they saw the information shown. The confirmation mechanism MUST be accessible according to WCAG 2.1 AA. If a request to give consent has no confirmation, the consent portal backend MUST refuse it, before any processing.

    Case Outcome
    Not confirmed button disabled
    Confirmed, and at least one scope chosen button active, consent recorded
    Confirmation undone again button disabled again
    Request to the backend without confirmation, for example directly on the API refused: CONFIRMATION_MISSING. No record, and no activation or transformation at BSNk
    Keyboard or screen reader only confirming and giving work

    Consent lifecycle requirements¶

    A consent has a limited validity. The lifecycle requirement covers the validity of a consent and its repeated use within that validity. The statuses that a citizen sees (Actief, Verlopen, Ingetrokken) and revocation are in citizen access and revocation and REQ-14.

    In the demo, the toestemmingsregister sets an absolute valid-until moment when it records the consent. It writes that moment into the consent proof as both valid_until and the expiry time exp. The PDP checks it at every request. A consumer can use a consent again and again within its validity. Single use is not built (SL-01b is blocked). Who sets the validity period is open again (Q-13).

    Consent initiation and return requirements¶

    A consent starts at the consumer. The consumer sends the citizen to the toestemmingsportaal with a request that names who asks what. After the choice, the portal sends the citizen back to the consumer with the outcome. The requirements cover that request, the data that the portal takes from the registration instead of the request, and the return.

    In the demo, the consumer sends the context as query parameters: consumer OIN, scopes, purpose, and return address. The portal keeps the context in the browser session during the mock login. It refuses a scope that it cannot describe, and shows only the requested scopes. On success, the proof goes back in the URL fragment. On refusal, the return carries status=denied. In demo v0.9.0, the consent portal backend does not check the request (ICTU/GBO-demo#427).

    REQ-37: A consent request names the consumer, the service, the requested data sets, and the return address¶

If an integrator acts on behalf of the consumer, the request MUST also name the integrator. These data MUST still be available after the citizen logged in. If an item is missing, the citizen MUST NOT see a consent screen. The same applies if the request asks for a data set that the consent service does not know.

    Role split between consent register and consent portal (S01/S02)¶

    The PSA splits the consent function into two capabilities: S01 consent registration (the toestemmingsregister) and S02 consent portal (the toestemmingsportaal: the portal UI inside MijnOverheid and the consent portal backend). The requirements for this split keep the BSN out of the register, and fix where the citizen identity comes from.

    In the demo, the consent portal backend receives the BSN from the validated portal token. It derives a reference to the citizen (an HMAC of the BSN). On the first consent, it asks BSNk for values. It sends only the reference and the encrypted values to the register. The register stores the polymorphic values under the reference. It is open whether register and backend stay two systems, and which of them is the BSNk participant (Q-49, ADR 0040, proposed).

    Citizen access and revocation requirements¶

    A citizen can see the consents that they gave and revoke them in the toestemmingsportaal inside MijnOverheid (FR-20, FR-22, FR-23). The requirements for this function cover these topics:

    • the overview of consents
    • the components that can reach the register for the overview
    • ownership
    • export
    • revocation
    • the notice about the rights of the citizen at the consumer

    In the demo, the consent portal backend derives the reference to the citizen (an HMAC of the BSN) from the validated portal token. The backend asks the register for the consents under that reference. It shows them as Actief (active), Verlopen (expired), or Ingetrokken (revoked). On a revocation, the backend checks ownership and asks the register to set the status to revoked. The record stays.

    Viewing and revoking do not call BSNk. The authorization chain denies the next request on a revoked consent with CONSENT_WITHDRAWN (REQ-14). The status names follow F-97. The status Opgehaald (retrieved) waits for Q-42.

    REQ-38: A logged-in citizen can view consents with status and revoke them¶

    The consent portal backend MUST let a citizen with a verified identity (REQ-24) view their consents and revoke a consent. The overview MUST order the consents by the moment of granting. It MUST hold the active consents, and the recently expired or revoked consents. For each consent, the overview MUST show the consumer, the purpose, the data sets, the validity, and the status. The data sets MUST show the same data elements as the consent screen showed before, without values.

    If the citizen has no verified identity, the backend MUST show nothing and change nothing. The status MUST follow from the register and the validity, on the same grounds on which the authorization chain denies.

    Detail of a consent for each set, the same data elements as on the consent screen, without values (proposal: not built)

    REQ-40: A citizen sees and revokes only their own consents¶

    At every overview, every view of one consent, and every revocation, the consent portal backend MUST determine the citizen from the verified identity (REQ-24). It MUST show or change only the consents of that citizen. The backend MUST NOT use a reference to a citizen that the request carries. The backend MUST refuse a revocation of the consent of another citizen before the register changes anything. The consent of another citizen and an unknown consent MUST get the same outcome: not found (CONSENT_NOT_FOUND). Then the answer does not reveal whether a consent exists.

    Revoke an own consent revoked (from code)
    Revoke the consent of another citizen refused: CONSENT_NOT_FOUND (HTTP 404), consent unchanged (demo: 403 consent_not_owned_by_caller)
    Revoke an unknown consent refused: CONSENT_NOT_FOUND (HTTP 404)

    Consent register data model¶

    The toestemmingsregister must keep certain data for production. The data model follows from the requirements. It is no requirement with its own number: every data item refers to the requirement or functional requirement that it follows from. Where an open question decides the model, the table marks an open place.

    The model says what the register knows. It does not say in which tables or which product. It is open whether the register and the consent portal backend (S01 and S02) are one system or two: Q-49.

    State: November 2, 2026. Demo: the schema of the demo (postgres_store.go#L15-L60) covers the core. Where the schema deviates, the item says so. The compose default runs the register in memory.

    The PostgreSQL store is optional (SL-12 is planned). With a persistent store, the register needs a fixed signing key (CONSENT_SIGNING_KEY_PATH), so that proofs stay valid after a restart (Q-55).

    Citizen¶

    The register keeps two data items about the citizen:

    Data item Content Basis
    Reference to the citizen An HMAC of the BSN under a secret key of the portal, with the key version in it. No BSN. REQ-20, route D
    Polymorphic values PI and PP of the first activation, under the reference. Once for each citizen. After that, only transformation. REQ-69

    The register does not keep the BSN. It also does not keep the encrypted identity (VI) and the encrypted pseudonym (VP) for each receiving party. It signs those into the proof and forgets them (REQ-69, REQ-80).

    Consent¶

    The register keeps these data items for each consent:

    Data item Content Basis
    Consent ID Own ID of the register. It is in the proof and is the key for the status query. REQ-68
    Citizen The reference to the citizen. REQ-20
    Consumer OIN of the dienstverlener to whom the citizen gave the consent. For an integrator, the represented party. REQ-12, REQ-106
    Use case The service from the catalog for which the consent applies. REQ-12, FR-32
    Scope per source For each source: the scope and the fields for which the citizen gave consent. One representation. A flat list of scopes can be derived from it. REQ-12
    Created Moment of granting. FR-22
    Valid until Absolute moment. The register keeps only the result. Where the period comes from (a default period for each service, bounds, and whether the citizen changes it) is open: Q-13. FR-05, FR-11, FR-32, REQ-19
    Status Active or revoked. An expired consent follows from "valid until". FR-22, FR-24, REQ-68

    The demo deviates from this model in three places:

    • Scopes are in the schema twice: as a flat list and as scope per source. Production needs only the scope per source.
    • The consumer chooses the validity period (validity_seconds). The default is one year, and the citizen cannot change anything: ICTU/GBO-demo#380.
    • The purpose comes from the redirect of the consumer. The register stores it as use_case, default hypotheek.

    Log of processings¶

    Every change produces an LDV record (REQ-72). The demo writes that record through an outbox in the same transaction as the change. So there is no consent without a log record. That is a choice of the demo and is no requirement.
