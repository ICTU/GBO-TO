    DvTP: the citizen gives consent¶

    In DvTP, the consumer is a private service provider (dienstverlener). A citizen at the consumer goes to the consent portal (toestemmingsportaal), logs in, and gives consent for one or more data sets. The result is a consent record in the consent register (toestemmingsregister) and a signed consent proof. The proof goes back to the consumer. The consumer uses the proof in DvTP query.

    For the concepts, see Consent and Pseudonymization. For the components, see Level 2: consent chain. The main decisions are ADR-0032 (the consent proof) and ADR-0040 (route D, proposed).

    Data per hop¶

    The tags in the last column are the data classes of What travels where. Each hop carries the following data:

    # From → to Endpoint In Out Data and notes
    1 Citizen → consumer frontend (UI) — — The consumer starts the request. No identity data travels at this hop
    2 Consumer frontend → portal frontend Redirect service, purpose, scope, client_oin, client_name, valid_until, return_url — Low: OIN and scope. All values are unsigned and come from the URL (useRedirectContext.ts#L29-L41). The portal checks only the return origin. REQ-111 asks for the name, the purpose, and the return address from the registration. For more information, see Q-60
    3 Citizen → portal frontend (UI) Login with the DigiD mock — The citizen types the BSN as the password. This shortcut exists only in the demo
    4 Portal frontend → portal backend POST /portal/login citizen_bsn — The BSN is in the browser and on the wire. In production, the identity comes from the MijnOverheid login (REQ-24, Q-50)
    5 Portal backend → portal frontend — — Portal token, HS256, sub = BSN The BSN is inside the token (auth.go#L17-L36). Later calls send this token instead of a raw BSN
    6 Citizen → portal frontend (UI) Data-set choice — One toggle per data set. The citizen cannot choose single fields (REQ-10). The portal shows only the requested sets
    7 Portal frontend → portal backend POST /portal/consents Portal token, dienstverlener_oin, scopes, validity_seconds, use_case — The body holds no BSN. The backend takes the BSN from the verified token. use_case is the redirect purpose (PortaalConsent.tsx#L77-L87). The consumer sets the validity (Q-13)
    8 Portal backend (internal) — BSN subject_ref The portal computes an HMAC of the BSN with its own secret, versioned key (subjectref.go#L40-L52, route D). The portal does not call BSNk
    9 Portal backend → register GET /subjects/{subject_ref}/polymorphic subject_ref — Medium: subject_ref. Only the portal asks for these values
    10 Register → portal backend — — 404 The register has no values, because this is the first consent of this citizen
    11 Portal backend → BSNk POST /v2/activate BSN, requester OIN and key set version of the portal — The portal sends the BSN to BSNk, once per citizen. The mock follows the BSNk interface, but uses JSON instead of SOAP (BSNK-11)
    12 BSNk → portal backend — — PI and PP Medium. Only the portal, as requester, can use them (BSNK-03)
    13 Portal backend → register PUT /subjects/{subject_ref}/polymorphic subject_ref, PI, PP — The register keeps PI and PP under the reference (REQ-69). The register gets no BSN and no per-party value
    14 Register → portal backend — — PI and PP Later consent: the portal finds the values again and does not activate (portal.go#L298-L321)
    15 Portal backend → BSNk GET /v2/bsn-authorisation-list — — The portal reads the list only when its copy is older than BSN_AUTHORISATION_LIST_MAX_AGE (default 1 hour, an assumption)
    16 BSNk → portal backend — — OINs that can receive the BSN The BSN authorization list (BSNK-06). If the copy is too old and BSNk does not answer, the portal gives no consent
    17 Portal backend → BSNk POST /v2/transform PP, per source EntityID (OIN), KeySetVersion, IdentifierType=Pseudonym — The portal makes this call for every source in CONSENT_SOURCES. One call holds at most four parties. More sources give more calls (BSNK-05)
    18 BSNk → portal backend — — VP per source Only its own source can read a VP (BSNK-08). In the demo, anyone can read the values, because the mock does not encrypt
    19 Portal backend → BSNk POST /v2/transform PI, per listed source EntityID, KeySetVersion, IdentifierType=Identity — The portal makes this call only for sources on the list. If no source is on the list, this call does not occur. A party can occur only once per call, so each form takes its own call
    20 BSNk → portal backend — — VI per listed source High at the recipient, and unreadable for others. This call and calls 17 and 18 work only while the citizen is logged in (BSNK-04)
    21 Portal backend → register POST /consents encrypted_subject (per OIN a pseudonym and, if listed, an identity, each with key_set_version), subject_ref, dienstverlener_oin, scopes, use_case, validity_seconds — The register never gets a BSN (REQ-23). Before this call, the portal writes its LDV record dataverwerking.bsn-pseudonimisering under subject_ref (portal.go#L153-L174, REQ-72)
    22 Register → portal backend — — consent_id, consent_token The register signs the proof and stores the record with dataverwerking.toestemming-verlenen in one transaction (main.go#L449-L484). It does not store the per-party values (REQ-80). For the proof claims, see The consent proof
    23 Portal backend → portal frontend — — consent_id, consent_token Medium-high: the proof. The payload holds no BSN
    24 Portal frontend → consumer frontend Redirect to return_url status=ok, consent_id in the query, consent_token in the fragment — The fragment does not reach a server log (PortaalBevestiging.tsx#L56-L64). The consumer cannot read the citizen from the proof (F-76). The question of what the redirect gives back is partly answered (Q-44)

    Error paths¶

    The consent flow has no policy decision. Each failure stops the flow before the register stores a consent. "No consent" means that the citizen stays in the portal and the consumer gets no redirect. If a row states a different result, the row applies. The consent flow has the following error paths:

    Main observations¶

    The consent flow in gbo-demo v0.9.0 has these properties and gaps:

    • The BSN boundary. The BSN occurs only in these places:

      • the browser and the portal token (hops 3 to 5),
      • the portal backend (hop 8),
      • BSNk, at the first consent (hop 11).

      The register and the consumer never see the BSN (REQ-20, REQ-23). The BSN in the browser is a demo shortcut.

    • One activation per citizen. At every later consent, the portal finds PI and PP under its own reference. Then the portal only transforms (TestASecondConsentOnlyTransforms). A new SUBJECT_REF_KEY gives every citizen a new reference. Migration to a new key is not built in demo v0.9.0 (Q-56).

    • No consumer identifier in the proof. The proof carries values that only the sources can read. The consumer does not recognize the citizen across consents (F-76). A VP for the consumer itself is not built in demo v0.9.0 (#478).
    • The proof freezes at consent. BSNk makes the values only while the citizen is present. As a result, the parties, the key versions, and the proof form are fixed for the whole validity (F-78, The proof freezes at consent). The portal configuration (CONSENT_SOURCES) names the sources. No catalogue supplies them (REQ-82).
    • BSNk recognition is open. Only a recognized party can activate and transform (BSNK-01). It is open whether the consent facility (toestemmingsvoorziening) can be a recognized party. It is also open whether the register and the portal backend are one BSNk participant (F-75, Q-26, Q-49).
    • The initiation is not provable. The consumer name, the purpose, and the return address come unsigned from the redirect URL (REQ-37, REQ-111, #427). The record holds the purpose as use_case. The proof does not hold the purpose (REQ-12, Q-69).

    • Some portal duties are not built. Demo v0.9.0 does not have these portal duties:

      • a step in which the citizen states that they saw the information (REQ-107),
      • a plain-language summary to the norm of REQ-117,
      • a separate confirmation of the choice to the citizen (REQ-122).

      It is open whether the portal must prove what the citizen saw (Q-51).
