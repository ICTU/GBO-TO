    Authorization in GBO Basis¶

    The Globaal Ontwerp calls this part "configurable authorization". Each source has a PDP that decides on every request, field by field, with rules written as policy. The FSC Inway of the source enforces the decision. This page shows the parts, the order of the checks, and the admission of parties. The Authorization concept page has the detail and the links to the code.

    Overview › GBO Basis › Authorization

    Five questions, five places¶

    Figure 2: PEP, PDP and PIPs at one source.

    The parts have these roles:

    Part Role
    PEP The FSC Inway. Its AuthZEN plugin sends every request with the raw body to the PDP and forwards the request only on an allow. There is no separate PEP service (ADR-0002).
    Request mapper Turns the GraphQL body into a list of fields with their arguments, following the FTV GraphQL profile. It does nothing else (ADR-0013).
    Policy Rego code that selects the regime, checks the consent proof and decides each field. The policy is data for the PDP, so a bronhouder changes it without a new build.
    PIP: consent register (toestemmingsregister) Gives the status of a consent for every request, over FSC. Gives the keys to check the proof. DvTP only.
    PIP: admission register Lists the admitted parties and the mandates of integrators. OpenFTV pulls it every five seconds.

    From query to decision¶

    The PDP takes a fixed series of steps for each request. The first step that fails decides the outcome:

    Three properties of this pipeline matter for the design:

    • Closed world. A field that no rule names is denied (NO_APPLICABLE_RULE). There is no separate catalog of allowed fields: the rules are the catalog (ADR-0009).
    • All or nothing. The PDP allows the request only if it allows every field. It never removes fields from a query.
    • Two layers of reasons. The consumer gets one coarse code, so it cannot learn the schema by trying field names. The administrator of the source sees the reason per field (REQ-06).

    Regime from evidence¶

    The evidence in the request selects the regime. A declared regime or a contract property plays no part (ADR-0031):

    Figure 4: Regime selection.

    The regime only selects which rules apply. Each rule still checks its own basis: DVT0001 denies without a verified consent, and the PID rules deny if a consent token is present.

    Only consent is positive evidence. A request enters the PID regime because it carries no token (F-70). For that reason, the PID rules admit only named callers: the EUDI adapter and the ASIP. These lists must never contain a DvTP consumer. The fix in the design is a verified PID as positive evidence (REQ-45).

    The rules¶

    Demo v0.9.0 has five rules. Each rule names its regime, the FSC services it serves, and the fields it can grant:

    Rule Regime Service Grants
    DVT0001 consent bri Income declaration fields, per consented year
    LVG0001 consent lvg The ownership check of the LVG pilot
    EUD0001 PID bri Income statement (inkomensverklaring) to the wallet, years 2024 and 2025
    EUD0002 PID brp Death certificate (akte van overlijden) to the wallet
    ASI0001 PID brp The BRP fields behind the ASI attributes, for the ASIP only

    A rule binds to a field only on its own services. A field name such as Query.ingeschrevenPersoon exists in several schemas. Without this binding, a rule for one source grants the same field at another source (REQ-97, F-90).

    Under consent, two checks look inside the query. The citizen must be the placeholder consent:identity, never a real number. Every requested year must have a consented scope, and a query without a year filter is denied. The PDP checks that the citizen comes from the proof. It never learns who the citizen is (F-77).

    Admission of parties¶

    Before a party can send requests, it needs an FSC contract. The FSC Manager of the source asks the same PDP whether to sign it. The contract policy reads the admission register and stops at the first failed check:

    Admission is data in a register, not a rule in the policy (REQ-61). An operator admits, pauses or widens a party without a policy change. A refused contract stays proposed, so the party can try again after admission (REQ-63). The contract decides who can connect. The request rules decide what each request can get (REQ-62).

    Open points¶

    The main open points in authorization are these:

    • The PID regime needs positive evidence of its own (F-70, REQ-45).
    • The ADL record does not hold the consent status that the PDP used, so a decision cannot be replayed from the record (F-72).
    • The FSC Inway of demo v0.9.0 loses the reason code on the way back to the consumer (detail).
    • How to model fields, recursion and arguments for future sources (Q-14).
