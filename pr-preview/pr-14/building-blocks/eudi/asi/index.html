    ASI provider¶

    The ASI provider lets a qualified trust service provider (QTSP) verify or retrieve attributes of a citizen at the authentic source. The exchange follows eIDAS article 45e and ETSI TS 119 478, clause 6.1. It is flow B of interaction pattern (interactiepatroon) A in the Globaal Ontwerp. GBO offers it as an OAuth front door with two services: the Authentic Source Interface Provider (ASIP) and its own authorization server (ADR-0037). The ASI verification runtime page has every hop and the links to the code.

    Each component has one job:

    Component Job In demo v0.9.0
    ASIP Offers verify and retrieve per data service at /<ds>/authsrc-api. Checks the DPoP-bound token first and takes the BSN only from the token (REQ-87). Seals every 200 response. Real
    Authorization server Registers a QTSP, shows the request page, runs the login, and issues a DPoP-bound token of 10 minutes for one data service. Real. It keeps the registered clients in memory.
    Wallet verifier The nl-wallet verification server. It runs the PID disclosure for the login and asks for the BSN (REQ-102). Real. It also serves the login of the reference QTSP, as a demo shortcut.
    DigiD mock A second means to log in. Stub. It checks for nine digits and gives only a BSN (F-88).
    Register of relying parties Holds the entitlement QEAA_Provider of each QTSP. Stub: a file
    Discover Interface An external role. Tells a QTSP which data service offers an attribute, from the records of the ASIP. Stub
    Reference QTSP An external role. Discovers, registers, gets a token, verifies, and checks the seal. Real client behavior. It is not a real QTSP.

    Trust boundary¶

    The QTSP and the source belong to two trust domains. The ASIP is the only part that acts in both:

    Figure 2: The trust boundary of the ASI route (F-87).

    The QTSP is an OAuth client of the authorization server. It has no FSC peer, no OIN and no PKIoverheid certificate. The reference architecture placed the interface in front of the FSC chain. The demo showed that this placement does not fit a QTSP, so the QTSP trust ends before FSC (ADR-0037).

    The admission of a QTSP has two parts (REQ-88):

    • The QTSP registers with a software statement, sealed with its certificate. The authorization server checks the chain and the organizationIdentifier.
    • The register entry must carry QEAA_Provider and the same organizationIdentifier. The server checks the entry again every hour (REQ-89). If the register does not answer, the client stays active (Q-34).

    The ASIP is an FSC consumer peer of its own, with a contract for the service brp at the source. For the PDP, the actor is always the ASIP. Rule ASI0001 grants the ASIP peer the fields of the Personal Records Database (BRP) behind the attributes, on brp only. The rule does not check the token or the QTSP. The PDP input and the ADL hold the BSN (REQ-60).

    The verify and retrieve flow¶

    A verification runs through discovery, registration, authorization with a login, the token, the query through GBO Basis, and the seal:

    Figure 3: Verify through the ASI provider, at essence level.

    The login is the approval (REQ-90). Before the login, the request page shows the legal name of the QTSP, the operation, the source, and the attributes (REQ-91). If the citizen refuses, no login takes place and the source gets no request.

    Retrieve runs the same way, with the scope retrieve. The request names attribute identifiers without values, and the sealed answer carries the values. If the source holds no value for one attribute, the answer is 404, without a partial result (REQ-101).

    After an accepted result, the reference QTSP issues a test statement to the wallet. It uses the issuance server of the PuB-EAA provider. The statement has a test marking and is not a QEAA.

    ETSI lets a response name one authentic source. Article 9(4) requires that the result names the responsible body (F-89, REQ-94). An authorization request names exactly one data service as resource, or the answer is invalid_target. The ASIP refuses a token for another data service with 401 (REQ-95). A QTSP that needs attributes of two sources authorizes twice, and the citizen logs in twice.

    By default, a token binds per operation, as ETSI specifies. A QTSP can also bind the token to the attributes with authorization_details. The ASIP then refuses any other attribute (ADR-0042, proposed, Q-33).

    Attributes described by the source¶

    The source describes the attributes that it offers, in the asi capability of its source document (ADR-0039). The ASIP has no source knowledge in its code:

    Each attribute has an identifier from the GBO catalog and the source fields per member of the value. Four operations build a value: pointer, join, const and each. A house number, for example, is three BRP fields. For each request, the ASIP replaces ...Selected with the fields of the requested attributes only (REQ-92).

    The identifiers and their value schemas are provisional until the EU catalog of attributes exists (Q-31). If the asi part has an error, the reconciler refuses the whole source, with its EUDI issuance. In demo v0.9.0, the authorization server takes its list of data services from configuration (AZSP_RESOURCES). The source descriptions do not feed that list (Q-38).

    Results and the seal¶

    The ASIP builds each value from the source fields and compares it with the value that the QTSP sent. Each attribute gets one of four results:

    Three rules apply to the results:

    • Unknown means only that the source holds no value (REQ-84). A chain that does not answer gives 503 (REQ-93). A PDP deny or GraphQL errors give 500.
    • A verify response holds no source value (REQ-85). MatchWithVariation also returns no value. The conformance matrix records that row as failing (F-92).
    • Fuzzy matching applies only to strings without a format (REQ-113).

    From January 1, 2027, every verification result must be sealed (REQ-83). The ASIP seals the exact body of every 200 response with a detached JWS in X-JWS-Signature (ADR-0041, proposed). It does not seal errors. The QTSP refuses a result without a valid seal. ETSI defines no seal format, so the format waits for a decision (Q-32). The demo seals with a development certificate, and it is open who holds the qualified seal certificate in production (Q-28).

    Compared with the Globaal Ontwerp¶

    The demo follows flow B of pattern A. It differs in four steps:

    Step Globaal Ontwerp Demo v0.9.0
    Authorization The verify and retrieve service uses the authorization facility (autorisatievoorziening) of GBO. The ASI provider has its own OAuth authorization server, as ETSI clause 6.1.3 describes (ADR-0037).
    Approval The wallet shows the request and asks for consent. The citizen logs in with the NL Wallet or the DigiD mock. The demo stores no approval (REQ-90).
    ISO 15000 A request over ISO 15000 needs no authorization. Clause 6.2 is not offered (REQ-112).
    After an accepted result The QTSP issues a QEAA. The reference QTSP issues a test statement that is not qualified.

    Open points¶

    The main open points in the ASI provider are these:

    • The QTSP can read the BSN in the access token (F-86, #595).
    • The register of relying parties and the certificate profile for QTSPs do not exist (F-85).
    • Nothing links the citizen who logs in at the QTSP to the citizen who logs in at the authorization server (F-93, Q-40).
    • The NL PID has no place of birth, and the DigiD mock gives only the BSN (F-94, F-88).
    • Who decides the seal format for all Dutch ASIPs (Q-32).
