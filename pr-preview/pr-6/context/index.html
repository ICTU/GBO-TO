    Context and scope¶

    The GBO technical system connects to external actors and systems. This chapter lists every koppelvlak on the system boundary and between GBO components. It covers the technical context only. The GO solution direction and the PSA solution direction give the business context: which parties exchange which data, and why.

    Technical context¶

    GBO has the same shape as in the Globaal Ontwerp: external parties use one of the channels, and every channel reaches the source through GBO Basis.     The koppelvlak inventory lists every interface with its protocol and code. The building block view zooms in per channel.

    Four points in these diagrams are easy to misread:

    • Only the portal backend calls BSNk, at consent time. Neither the PDP nor the source gateway calls BSNk. The source reads its own value with its own decryption component (ADR-0033).
    • The PDP gets the consent status over FSC: from its own Outway (peer …0800) to the register's Inway (peer …0700). Only the public keys come directly from the register (ADR-0032).
    • The QTSP is not an FSC participant. It is an OAuth client of the ASI authorization server and calls the ASIP over HTTPS. The ASIP is the FSC participant toward the source (F-87, ADR-0037).
    • The ASI has four roles. GBO provides the ASIP and the authorization server. The Discover Interface and the QTSP are external. For these two roles, the demo has a stub and a reference client. It is open who operates the ASIP and the authorization server (Q-37).

    Koppelvlak inventory¶

    Every interface has a row in one of the tables in the following sections. A row gives the standard that the interface follows and its implementation in gbo-demo. Rows marked designed are not built in demo v0.9.0. Paths in the last column are relative to gbo-demo v0.9.0.

    DvTP consent¶

    The DvTP consent chain uses these interfaces:

    Koppelvlak Between Protocol and standard Implemented in
    Consent initiation Consumer → toestemmingsportaal, and back HTTPS redirect with consumer, scopes, purpose, and return URL. The return carries the consent proof in the URL fragment, or status=denied (REQ-37, REQ-119). toestemmingsportaal-frontend
    Citizen login Citizen ↔ toestemmingsportaal DigiD (mock): the citizen types a test BSN, and the backend signs a portal token with the BSN in sub. Real DigiD gives the identity in an assertion (REQ-24). portalhttp
    Consent registration Portal backend ↔ toestemmingsregister REST: POST /consents, GET /consents?subject_ref=…, GET and DELETE /consents/{id}, GET and PUT /subjects/{ref}/polymorphic. No BSN crosses this interface (REQ-23, REQ-39). consent-register/main.go
    BSNk PP Portal backend → BSNk /v2/activate, /v2/transform, and /v2/bsn-authorisation-list. The mock follows the BSNk interface as JSON and does not encrypt. Production BSNk uses SOAP with PKIoverheid (BSNK-11). bsnk-mock
    Consent proof Consumer → Inway → PDP and source gateway Signed JWT gbo-consent+jwt (ES256) in the X-GBO-Consent-Token header, with encrypted_subject per source. The query names the subject with the placeholder consent:identity or consent:pseudonym (REQ-79, AV-05). consent_token.go
    Consent keys PDP → toestemmingsregister GET /.well-known/jwks.json, cached for 300 s consent.rego
    Consent status PDP Outway (…0800) → register Inway (…0700) FSC service consent-status: GET /consents/{id}/status on a status-only listener, with no cache and a 2 s timeout. The register refuses a call without an FSC peer (REQ-76). status.go, Makefile

    Authorization and FSC¶

    The authorization chain and the FSC group use these interfaces:

    Koppelvlak Between Protocol and standard Implemented in
    Data request Consumer Outway ↔ bronhouder Inway FSC (OpenFSC v2.4.0): mTLS, access token, and grant hash. Grants carry no properties. fsc-infra
    Delegated data request Integrator Outway ↔ bronhouder Inway FSC DelegatedServiceConnectionGrant, signed by the integrator, the represented consumer, and the provider (REQ-106) seed-bri-delegation-int.sh
    Authorization Inway (PEP) ↔ PDP OpenID AuthZEN 1.0, POST /authzen/v1/evaluation over HTTPS. The Inway passes the raw body, and the PDP maps it per the FTV GraphQL profile (REQ-42). openftv-pdp
    Contract decision Provider Manager → PDP AuthZEN autosign request for each submitted contract (REQ-62) autosign.rego
    Participant admission PDP ← admission register OpenFTV PIP pull, GET /internal/openftv/participants, every 5 s, on a network that only the PDP shares (REQ-61) dvtp-onboarding.yaml

    Bronhouder¶

    The bronhouder uses these interfaces:

    Koppelvlak Between Protocol and standard Implemented in
    GraphQL source API Source gateway ↔ source GraphQL over HTTP, POST /graphql. Only the Inway can reach the gateway (REQ-81). graphql-server, brp-graphql-server, lvg-graphql-server
    Source decryption Source gateway → decryption component of the source POST /signed-encrypted-identity and POST /signed-encrypted-pseudonym. The component calls no other service (REQ-21). decryption.go
    Source metadata Reconciler ← source GET /.well-known/gbo over a separate FSC metadata service, per gbo-source-metadata 1.0 or 1.1 (REQ-64) schema, source_metadata.go

    EUDI issuance¶

    EUDI issuance uses these interfaces:

    Koppelvlak Between Protocol and standard Implemented in
    Wallet issuance EUDI wallet ↔ issuance server OpenID4VCI with OpenID4VP disclosure, SD-JWT VC (dc+sd-jwt) eudi-issuance-server (nl-wallet v0.5.0)
    Attestation data Issuance server → EUDI adapter POST /attestations/{source_id}/{type_id} over public HTTPS. In demo v0.9.0, this route has no caller authentication (REQ-45, #133). source_release_runtime.go
    Offer catalog Frontends ← EUDI adapter GET /eudi-offers.json. If a source is stale, the adapter returns 503. source_release_runtime.go
    Type metadata Wallet ecosystem ← EUDI adapter GET /types/{source-id}/{type-id}/v{n}, immutable, vct#integrity type_metadata.go
    Source registry EUDI adapter, issuance init step, ASIP ← source registry PostgreSQL, read-only role on releases and the active pointer source-registry
    QTSP test statement Issuance server → reference QTSP Callback on a secret path over CA-pinned HTTPS (use case qtsp-attestation). Demo scaffolding. qtsp_issuance.go

    Authentic Source Interface¶

    The Authentic Source Interface uses these interfaces:

    Koppelvlak Between Protocol and standard Implemented in
    ASI discovery QTSP ↔ Discover Interface, and Discover Interface ← ASIP records ETSI TS 119 478 clause 5.3 and Annex A. dataService records (clause 5.3.3) at /<ds>/dataservices (REQ-99). asi-discovery-stub (stub), asi-provider
    ASI contract QTSP ← ASIP ETSI Annex B OpenAPI with completions. x-oauth-authorization-server names the authorization server (REQ-100). asi-provider/openapi
    ASI server metadata QTSP, ASIP ← authorization server RFC 8414 metadata and JWKS asi-authorization-server
    QTSP registration QTSP → authorization server RFC 7591 POST /register with a software statement sealed by the QTSP certificate (x5c, registryURI) (REQ-88) asi-authorization-server
    Entitlement lookup Authorization server → register of relying parties Lookup on registryURI for the entitlement QEAA_Provider (CIR 2025/848). The demo reads a stub file (F-85). register.json
    ASI authorization Citizen browser ↔ authorization server ↔ QTSP OAuth 2.0 code flow, PKCE S256, RFC 8707 resource (exactly one data service), optional RFC 9396 authorization_details (REQ-90, REQ-95) asi-authorization-server
    Citizen identification Wallet ↔ wallet verifier ↔ authorization server OpenID4VP, PID urn:eudi:pid:nl:1. A DigiD mock is the second means (REQ-102). asi-wallet-verifier, digidmock
    ASI token Authorization server → QTSP → ASIP RFC 9068 JWT (ES256), DPoP (RFC 9449), private_key_jwt (REQ-86, REQ-87) accesstoken
    ASI verify and retrieve QTSP ↔ ASIP ETSI TS 119 478 clauses 6.1.1 and 6.1.2 at /<ds>/authsrc-api/verify and /retrieve. Errors follow RFC 9457. The seal is in X-JWS-Signature (detached JWS) (REQ-83, REQ-112). handler.go
    ASIP source query ASIP Outway (…1200) ↔ provider Inway FSC and AuthZEN (rule ASI0001). One GraphQL query per request. graphqlsource
    ASI source description Reconciler ← source, and ASIP ← source registry gbo-source-metadata 1.1, capability asi. The ASIP reads a release snapshot. asi-mapping, source-registry

    Logging and audit¶

    Logging and audit use these interfaces:

    Koppelvlak Between Protocol and standard Implemented in
    Decision records PDP → ADL, and reader → ADL Logius ADL in Postgres ftv_adl. Readers use a SELECT-only role (REQ-71). adl-reader.sql, adl.go
    Processing records Component → logbook of its controller LDV v1.0.0 write, POST /logboek/records, over HTTPS with JSON and a bearer write token (REQ-72) ldv-client
    Processing-record read Auditor, portal → logbook LDV read extension, POST /data-processing-operations on trace ID, processing activity, or data subject. A read is possible with a read token only. ldv-logboek
    Transaction logs Auditors ← txlog of each peer FSC txlog API, GET /v1/logs over mTLS. The demo reads the txlog API inside each organization. Access in production is an open question (F-42, Q-08). fsctxlog.go
    Trace context Every component → next hop W3C traceparent. Fsc-Transaction-Id is recorded next to it (REQ-55). tracecontext.go
    Telemetry All services → collector OpenTelemetry OTLP collector-config.yaml

    Scope¶

    The demo implements three trajectories end to end, at demo grade:

    1. The DvTP query under consent, with an integrator variant and the LVG pilot as a second consumer and source.
    2. EUDI issuance of PuB-EAA attestations.
    3. ASI verification and retrieval for QTSPs (ETSI TS 119 478 clause 6.1).

    Two trajectories are design-level: SDG-OOTS and Gov-to-Gov. The runtime view has a scenario for each.

    This design covers the following parts of the system:

    • the authorization chain: PEP, PDP, PIPs, policies, and contract decisions
    • the consent chain: portal, register, consent proof, and status service
    • pseudonymization at consent time and decryption at the source
    • the FSC group configuration and the admission register
    • EUDI issuance, source onboarding, and the source registry
    • the Authentic Source Interface: ASIP, authorization server, and discovery records
    • logging, audit, and observability

    The following parts are out of scope:

    • the internal architecture of bronhouder systems behind the GraphQL API
    • the EUDI wallet, DigiD, and BSNk themselves
    • the QTSP, the Discover Interface, and the national register of relying parties
    • the relying-party side of wallet presentations, which touches no GBO infrastructure
    • the EU OOTS common services

    The developer tooling of the demo is scaffolding: the developer portal, the consumer mocks, keyper-mock, and the reference QTSP. This tooling is outside the target architecture. The deployment view marks each unit as target architecture or scaffolding.
