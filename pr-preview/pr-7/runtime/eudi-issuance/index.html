    EUDI issuance: the PuB-EAA route¶

    A citizen scans a QR code, shares the PID from the NL Wallet, and gets an attestation with data from an authentic source. The bronhouder is the PuB-EAA provider. GBO operates the technical issuance facility (ADR-0028, PSA S11). The decision for this route is ADR-0018.

    One issuance in gbo-demo v0.9.0 has hops, data on each hop, and error paths. The following sections give these details and do not explain the concepts again. For the concepts, see these pages:

    • The components: Level 2: EUDI chain.
    • The regime: Regime selection.
    • The source description and its release: Source onboarding.
    • The certificates: EUDI trust roles.
    • The BSN in this route: Exception: the BSN in the EUDI and ASI routes.

    Before the first QR code¶

    The route runs only from an active source release. For each source, the release holds these items:

    • The offers.
    • The GraphQL query and its parameters.
    • The claims.
    • The display texts.
    • A reference to the certificate set.

    GBO generates the issuance configuration and the Type Metadata from the release (REQ-64, ADR-0016, ADR-0017). A valid FSC contract does not activate a source (REQ-65). For that run, see Admission and activation. If no release is active, no offer exists and the portal shows no QR code.

    The demo has two attestation types:

    Type Source (source_id) FSC service Rule Offers Subject of the data
    Inkomensverklaring belastingdienst bri EUD0001 jaar 2024 and 2025 The PID holder
    Akte van overlijden rvig brp EUD0002 One, without parameters The deceased partner of the PID holder (related-person attestation)

    The offers come from the source documents (BD, BRP). In the default demo, both sources are on the Belastingdienst peer …0200 (FSC peers).

    Data per hop¶

    The table marks personal data in bold. The hop numbers refer to the steps of the sequence:

    # From → To Endpoint Data Notes
    1 to 2 Portal → adapter GET /eudi-offers.json (through the portal proxy) Per offer: key, label, source_id, type_id, and parameters No personal data. The adapter serves the offers of the active release (source_release_runtime.go#L95-L104, nginx.conf#L43-L49).
    3 to 4 Citizen ↔ portal — In: the chosen offer. Out: a universal link with request_uri The portal builds the link in the browser (eudi.ts#L42-L51). The QR code is public, so any person can scan it. This is the only initiation route in the demo.
    5 to 7 Wallet ↔ issuance server POST /disclosure/<offer>/request_uri The disclosure request The request asks for one PID claim, bsn (issuance_config.go#L162). The reader certificate of the source names the issuer and the purpose (REQ-58).
    8 to 10 Wallet → issuance server OpenID4VP PID with the BSN The issuance server checks the presentation against issuer_trust_anchors (issuance_server.toml.example#L3-L9). That list also holds non-PID anchors (REQ-45). The approval in the wallet is no legal basis (F-83).
    11 Issuance server → adapter POST /attestations/{sourceID}/{typeID}?<offer parameters> Disclosed attributes, urn:eudi:pid:nl:1 with the BSN Public HTTPS (an ISRG-rooted certificate, through a tunnel). The route has no caller authentication (source_release_runtime.go#L69-L81, #133). For more information, see The callback gap.
    12 Adapter (internal) Active release In: path and body. Out: the BSN The binding of sourceID and typeID must exist in the active release. The adapter takes the BSN from the PID and does not check a signature (main.go#L143-L162, #L23-L26).
    13 Adapter → logbook LDV write Record dataverwerking.pid-bsn-extractie The record names the data subject by a pseudonym that is local to the logbook. It does not hold the BSN. If the logbook does not acknowledge the record, the adapter does not call the source (main.go#L256-L262, ldv_issuance.go#L101-L147, REQ-72).
    14 Adapter (internal) Query plan In: the offer parameters and the query of the release. Out: {query, variables: {bsn, jaar}} The parameters must match a published offer exactly (source_metadata.go#L272-L298). The adapter has no query or mapping of its own (REQ-44).
    15 Adapter → edi-outway POST {outway}/graphql {query, variables} with the BSN, and the headers Fsc-Grant-Hash, Fsc-Transaction-Id, and traceparent The adapter checks that the source document names the contracted service (main.go#L466-L503). No X-GBO-Scope and no flow. The txlog and the trace carry the transaction ID. The ADL record behind the Inway gets its own trace and no transaction ID (#369, REQ-55, ADR-0035).
    16 to 17 edi-outway ↔ edi-manager FSC access token In: the grant hash. Out: a certificate-bound token The Outway caches the token. The grant carries no properties.
    18 edi-outway → bd-inway FSC, mTLS Body 1:1 with the BSN Every channel goes through FSC with a valid certificate (REQ-46).
    19 bd-inway → PDP POST /authzen/v1/evaluation AuthZEN envelope: Outway peer …0100, service bri, and the body with the BSN The Inway is the PEP. The mapper parses the GraphQL and does not call BSNk (Regime selection).
    20 PDP → bd-inway AuthZEN response Allow or deny, per field The request has no consent token, so the PID regime applies. EUD0001 checks the designated issuer, the BSN in the root argument, and allowed_years (eud0001.rego#L45-L75, REQ-74, REQ-97). The PDP writes the BSN to the ADL and the console decision log (REQ-60).
    21 to 22 bd-inway → gateway → source POST /graphql The judged query with the BSN The request has no consent token, so the gateway passes it through unchanged (Level 2: bronhouder). The source logs its own processing.
    23 Source → adapter GraphQL response Income data for the year Back through the same FSC chain, 1:1.
    24 Adapter (internal) gbo-simple-v1 In: the response at result_pointer. Out: flat claims Exactly one result gives claims. Zero results is no_data. Any error gives no attestation (REQ-116). Only scalar claims (REQ-78).
    25 Adapter → logbook LDV write Record dataverwerking.attestatie-samenstellen The record names the number of claims without their values. It points at the logbook of the source. The adapter writes it for every outcome after the call to the source. If the logbook does not acknowledge the record, the adapter withholds the answer (main.go#L283-L292).
    26 Adapter → issuance server Response to hop 11 [{attestation_type: <VCT>, attributes, format: "dc+sd-jwt", id}] with the claims The VCT is the URL of the generated Type Metadata (main.go#L319-L334).
    27 to 28 Issuance server → wallet OpenID4VCI Attestation (SD-JWT VC) Signed with the issuer certificate of the source. Valid 365 days, with one status list per type (issuance_config.go#L166-L180, REQ-77). The wallet shows the issuer from the certificate.

    Public endpoints of the adapter¶

    The adapter serves three routes on one listener (source_release_runtime.go#L59-L106):

    Route Caller Content When the release is not available
    GET /eudi-offers.json Developer portal, consumer frontends The offer catalog 503 for all sources, also when only one source is past its grace period
    GET /types/{sourceID}/{typeID}/v{version} Wallet, relying parties The SD-JWT VC Type Metadata that GBO generates from the claims. Its URL is the VCT. 503
    POST /attestations/{sourceID}/{typeID} Issuance server The attestation callback 503

    The issuance server installs the same Type Metadata bytes and computes vct#integrity over them. A change to the claims or the display needs a different type_version (type_metadata.go#L17-L40, The eudi capability).

    The callback gap¶

    The issuance server checks the PID. The adapter does not know that the request comes from the issuance server. No mechanism binds the BSN in hop 11 to a checked disclosure (REQ-45, Q-18, #133). The demo uses this gap itself. The developer portal has a playground that posts a typed BSN to the adapter (EudiQrPanel.tsx#L36-L51, nginx.conf#L36-L42).

    sequenceDiagram autonumber box rgb(241,239,232) Caller participant X as Any caller<br/>that reaches the adapter end box rgb(255,237,213) EUDI participant AD as EUDI adapter end box rgb(220,252,231) GBO Basis participant OW as edi-outway<br/>(designated issuer) participant PDP as PDP<br/>(EUD0001) end box rgb(221,235,247) Source participant SRC as Source end X->>AD: POST /attestations/belastingdienst/inkomensverklaring?jaar=2024<br/>body with any BSN, no wallet AD->>OW: Query with that BSN OW->>PDP: Actor …0100, no consent token PDP-->>OW: Allow: designated issuer, BSN present SRC-->>AD: Income data of that person AD-->>X: Claims, without any wallet

    The data on each hop of this gap is as follows:

    # Data Notes
    1 Any BSN No caller authentication, and no proof of a checked disclosure.
    2 to 4 BSN The request has no consent token, so it enters the PID regime. The only gate of this regime is the list of designated issuers (F-70, eudi_helper.rego#L13-L30).
    5 to 6 Income data The caller gets the projected claims.

    SL-25 removed the PID check from the adapter, because the issuance server checks the PID. The issuance server checks the signature, so the gap is in the callback. REQ-45 names two fixes:

    • The adapter checks the SD-JWT itself.
    • The issuance server authenticates the callback and delivers signed evidence.

    Both fixes need the binding of the disclosure to the request. The reference QTSP callback on the same issuance server uses a secret path over CA-pinned HTTPS (qtsp_issuance.go#L134-L152, ASI verification).

    Error paths¶

    The consumer of the adapter is the issuance server. The issuance server gets only the HTTP status. The details are in the adapter log (stage). For a PDP deny, the details are also in the ADL.

    The FSC Inway removes the reason of a deny (ftv-graphql-profile.md#L93-L95). In every error path, no attestation reaches the wallet. The error paths have these triggers and outcomes:

    Trigger Outcome Pinned by (v0.9.0)

    The adapter cannot load a release 503 source activations unavailable source_release_runtime.go#L70-L74
    sourceID or typeID not in the active release 404 source_release_runtime.go#L75-L79
    Source metadata missing, expired, or past the stale grace (15 min fresh, 1 h grace) 503 source metadata unavailable, for this source only (REQ-66) main.go#L221-L225, source_metadata_cache.go#L10-L14
    Body unreadable, or no disclosed attestation in it 400 main.go#L234-L246
    PID without a BSN 400 no BSN in disclosed PID. The adapter logs nothing and does not call the source. main.go#L249-L253, ldv_test.go#L402
    The logbook does not acknowledge the LDV record of hop 13 500. The adapter does not call the source. main.go#L256-L262, ldv_test.go#L354

    Related-person attestation: akte van overlijden¶

    The akte van overlijden holds data about the deceased partner of the citizen who shares the PID. The subject of the claims differs from the person who discloses the PID (F-47, REQ-57, SL-43). The run is the same as the run in the preceding sections, with these differences per hop:

    # Difference
    11 POST /attestations/rvig/akte-van-overlijden, without parameters.
    14 to 15 The query is akteVanOverlijden(bsn: $bsn) with the BSN of the PID holder, on service brp.
    19 to 20 EUD0002 decides. It grants a closed list of output fields and checks the BSN in the root argument. It has no year check (eud0002.rego#L20-L66).
    21 to 22 The gateway is brp-sidecar, and the source is brp-graphql-server.
    22 to 23 The source resolves the relation itself. It selects the marriage that ended by the death of the partner. If the partner died on a different date than the dissolution, the source returns nothing. Then the adapter answers 404 (main_test.go#L183).
    25 The deceased is not a data subject under the GDPR. The source logs the requester and the living parents (AV-10).

    The PDP sees only the flat output of the source view. It does not see the relation. The relation depends on the source and on the subject from the PID. Because of the callback gap, a caller can ask for the akte for any BSN.

    The preferred design puts the relation in filter arguments of the published schema. The policy then requires these arguments with fixed values (#425, Q-14). In demo v0.9.0, the source description does not mark the relation.

    Observations¶

    The run of an issuance in demo v0.9.0 shows these facts:

    • The regime follows from the evidence. A request without a consent token goes into the PID regime. That regime has no positive evidence of its own. Its only gate is the list of designated issuers. This list must stay disjoint from the consent consumers (REQ-74, F-70, ADR-0031). A test pins the disjointness only for the seeded consumers (engine_test.rego#L366-L376).
    • The PID check and the source query have no link. The issuance server checks the PID. The adapter callback has no authentication (REQ-45, Q-18). The PID trust list also trusts the GBO development CA and the issuer CA of every source.
    • The BSN is in the decision logs. The adapter puts the plain BSN in the query variables. As a result, the BSN is in the PDP input, the ADL, and the console decision log (REQ-60, F-54, ADR-0043, #368). The LDV records of the adapter hold no BSN.
    • The offer and the policy are independent limits. The source offers 2024 and 2025. EUD0001 allows 2024 and 2025. A request for 2023 fails at the adapter (no offer). The PDP also denies it (YEAR_NOT_ALLOWED). Publication by a source does not authorize the published data (F-74).
    • The adapter holds no knowledge of a source. The query, the parameters, the claims, the display, and the Type Metadata come from the release (REQ-64, F-57). The source decides through its own PDP (REQ-44).
    • No partial attestation exists. Any projection error gives 502 and no attestation (REQ-116). The issuance server sees no reason code.
    • The validity is fixed. Every source attestation is valid 365 days. GBO has no change feed from the source. As a result, GBO cannot revoke an attestation when the source data changes (REQ-77, F-82).
    • Correlation works, with one gap. The adapter sends one Fsc-Transaction-Id and a traceparent. The txlog, the LDV records of the adapter and the source, and the trace share them. The ADL record behind the Inway has its own trace and no transaction ID (#369) (REQ-55, Reading a chain).

    Not built in demo v0.9.0¶

    Demo v0.9.0 does not have these items:

    • An authenticated callback, and the binding of the disclosure to the source query (#133, REQ-45).
    • A PID trust list with PID-provider anchors only.
    • The BSN out of the PDP input (#368, ADR-0043, proposed).
    • Validity and revocation per type, set by the bronhouder, with revocation on instruction or on a change in the source (REQ-77, AV-12, AV-13).
    • Nested claims (REQ-78), and traceability of the mapping version per attestation (REQ-124).
    • The relation as filter arguments, and its marking in the source description (#425, REQ-57).

    • The regulatory frame for PuB-EAA issuance (F-81, Q-28). This frame has these parts:

      • Designation.
      • A registration certificate.
      • A qualified seal in a QSCD.
      • Conformity with ETSI TS 119 471 and TS 119 472-3.

      The trust list for PuB-EAA providers is open (Q-30). Key custody is open (Q-17).

    • A second initiation route next to the QR code in the developer portal.

    • Cross-route items from the ASI work (ASI verification):
      • The BRP document also publishes the asi capability. An error in asi refuses the whole source, and this includes its EUDI issuance (#592, source-onboarding.md#L400-L401).
      • The issuance server also issues the test statement of the reference QTSP. That use case runs only in the local stack. A deployment in the simulation environment is #594.
      • #595 (BSN in the ASI token) and #596 (same-device wallet login on a phone) concern only the ASI route.
