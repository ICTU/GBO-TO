    Design to demo matrix¶

    This matrix lists the design elements of four sources:

    • the Globaal Ontwerp (GO),
    • the Project Start Architectuur (PSA),
    • the functional requirements for DvTP (FR-DvTP v0.9),
    • the EUDI regulation.

    For each element, the matrix records if the GBO demo covers it, and gives the evidence. The findings and the open questions give the reverse direction, from demo to design.

    Each row has a status, an evidence link, and a note on the state of the demo. The notes link to the requirements, findings, open questions, demo increments, and ADRs that explain the row. The port to the TO on November 2, 2026 brought the evidence and the notes up to demo v0.9.0. No status changed.

    Coverage summary¶

    The summary counts the rows on this page. It does not count the historical rows of the reference architecture.

    Group ✓ ◐ ○ In scope Hook or out Rows

    B: open decisions 0 12 2 14 5 19
    FR: FR-DvTP v0.9 8 22 7 37 2 39
    Total 19 74 18 111 10 121

    Of the 111 in-scope rows, 17% are covered, 67% are partial, and 16% are not covered.

    Most partial rows can become covered only after a governance decision or with production infrastructure. Three examples of such rows are:

    • the LDV schema and retention (Q-08),
    • the link of organization identifiers in PSA S04,
    • PKIoverheid certificates instead of the demo CA (the direction is answered in Q-07).

    Three items of concrete demo work are open in demo v0.9.0:

    • validate a policy set before activation (F-52),
    • admission per service (#382),
    • the BSN in the ASI token (#595).

    Legend¶

    The status column uses five symbols:

    Status Meaning
    ✓ Covered: the feature works end to end in the demo, with evidence.
    ◐ Partial: some parts are covered, and the rest is open.
    ○ Not covered: in scope, but not built.
    — Out of scope or hook: deliberately not in v1.
    ? To be checked against the demo. In demo v0.9.0, no row has this status.

    The scope column uses five values:

    Scope Meaning
    Base The shared foundation for all routes: PEP, PDP, PIP, connectivity, audit, and semantics.
    DvTP Specific to the consent route (data sharing with third parties).
    EUDI Specific to the EUDI wallet routes: issuance (PuB-EAA) and verification for QTSPs (ASI).
    Hook Not in v1, but the demo keeps an extension point open.
    Out Not relevant for the v1 demo.

    The evidence column follows three rules:

    • A status is valid only with evidence. The evidence is a link to the demo at v0.9.0, a demo pull request or issue, or a requirement that carries the evidence.
    • Some links pin an older demo commit. They are historical evidence for the state at the time of the check.
    • FR-DvTP v0.9 is not public. The matrix names its criteria without a link.

    Architecture principles (P-01 to P-16)¶

    Source: PSA architectuurprincipes. These principles are invariants: the demo must not break them.

    ID Title Scope Status Evidence Notes
    P-01 Legal basis before exchange Base ◐ REQ-68, REQ-14, REQ-19 Before an allow, the PDP checks that the consent is valid, unexpired, and not revoked. A legal-basis path (government to government) is out of scope.
    P-02 Minimal data processing Base ◐ REQ-08, REQ-17 The PDP decides each field of the parsed query (SL-03a). Under a consent, the subject comes only from the proof (REQ-79).
    P-03 Privacy by design and by default Base ◐ REQ-80, REQ-21, REQ-23, REQ-69, REQ-82 The register holds no BSN. The proof carries an encrypted value per source, and the consumer gets no identifier (SL-51). In the demo, BSNk is a mock, and the pseudonym form is open (Q-01).
    P-04 BSN-free for private consumers DvTP ✓ consent_token.go#L47 (no plain BSN in the proof), decryption.go#L76 (the source decrypts its own value) The consumer has no identifier at all: it sends a placeholder, and the source replaces it after the allow (REQ-79, REQ-80, SL-51). F-76 describes the effects on logging and recognition.
    P-05 Recognized authentication means at an adequate level of assurance Base ○ DigiD mock in the toestemmingsportaal (DigiDAuth.tsx), ASI authorization server with DigiD mock and NL Wallet (client.go#L119) The demo has no real means at a set level of assurance. Real means are out of scope. Q-36 asks which level ETSI TS 119 461 requires for the ASI route, and if DigiD meets it.
    P-06 Support for the EUDI wallet Hook — — The principle row stays a hook. The wallet routes are in the EUDI rows.
    P-07 Trust through recognized admission and trust anchors Base ◐ fsc-infra/pki, REQ-67 The demo runs real OpenFSC with mTLS and its own CA (SL-34a). The certificate carries the legal identity (SL-49, F-60). Open: PKIoverheid certificates instead of the demo CA (direction answered in Q-07). Also open: the issuing model, with one certificate set or a set per source (#225).
    P-08 Record once, use many times Base ◐ REQ-11 The source stays authoritative, and GBO components keep no copy. The demo does not show reuse explicitly.
    P-09 Open standards and vendor independence Base ◐ docker-compose.yml GraphQL, OPA, AuthZEN, OpenFSC with mTLS, OTel, OpenID4VCI, and OpenID4VP are open standards. The GraphQL profile for FSC is a proposal and has no standard status (B-02).
    P-10 Data sovereignty: the bronhouder keeps control Base ◐ source_metadata.go#L101 (validation of the source description), dvtp-onboarding-register, autosign.rego#L171 The source decides who connects (SL-45), what is available (REQ-64, F-57), and when (REQ-65). The PDP behind the source Inway checks each request (F-06 closed). In demo v0.9.0, REQ-64 is built for EUDI and the ASIP (#592). It is not built for DvTP.
    P-11 FAIR principles for data Base ◐ REQ-64, AV-07 Findable and accessible: each source publishes a versioned description at a fixed location. Not interoperable or reusable: the mapping is per source, with no canonical model (Q-11).
    P-12 Logging and non-repudiation Base ◐ docker-compose.yml#L125 (ADL), adl.go, ldv-logboek The ADL is the audit source (REQ-71), with an LDV logbook per system (REQ-72) and one trace ID (REQ-55). Open: the BSN in both decision logs (REQ-60, F-54, #368), field detail only in the console log (F-72), and production guarantees (Q-08, F-07).
    P-13 Transparency and access for the citizen DvTP ✓ REQ-38, REQ-39, REQ-40 For each consent, the citizen sees who, what, purpose, and duration, and can revoke the consent (SL-06a, SL-06b). Missing: usage status (F-19) and processing per consent (Q-25).
    P-14 Separation of generic and specific functions Base ◐ REQ-44, REQ-92 Each capability is a service of its own, and the front ends call it directly (SL-11, SL-15). The EUDI adapter holds no use-case knowledge (SL-46). The generic chain also runs behind the ASIP (F-87).
    P-15 Decoupling for agility Base ◐ gbo-pdp.yaml Policy changes reach the PDP as a bundle, without a new PDP image (SL-44, RL-01). Mostly covered.
    P-16 Transparent access for private parties Base ◐ dvtp-onboarding-register, autosign.rego#L171 Admission is a registration, and each contract proposal gets an explicit decision with reasons (REQ-61, REQ-62, REQ-63). Missing: the grounds (FR-30), an objection procedure, and admission per service (F-56, #382). Q-22 gives the answer on grounds and granularity.

    Design principles (D-01 to D-14)¶

    Source: PSA ontwerpprincipes.

    ID Title Scope Status Evidence Notes
    D-01 Decentral where possible, central where necessary Base ◐ fsc-infra/docker-compose.yml#L773 (one shared PDP) One shared PDP behind all Inways is a demo shortcut. A PDP per source is possible with bundles (SL-44). Q-02 is answered: federated, per bronhouder.
    D-02 Agreements before standards before facilities Base ○ — This is governance, and the demo cannot show it.
    D-03 Use national generic facilities (GDI) unless Base ○ — DigiD, BSNk and MijnOverheid are mocks. Real GDI facilities are out of scope.
    D-04 Robust, modular, and flexible design Base ◐ services/ The services are modular. Some services run in memory or as a mock.
    D-05 Data at the source, no unnecessary copies Base ✓ REQ-11 GBO components fetch per request from the source and keep no copy.
    D-06 Component-based working Base ✓ services/ The services are separate and reusable.
    D-07 Open source unless Base ✓ docker-compose.yml All components are open source.
    D-08 Comply or explain: mandatory open standards Base ◐ — The demo uses GraphQL, JWT, OTel, and FSC with mTLS. The GraphQL profile for FSC is open (B-02).
    D-09 API-first Base ✓ graphql-server, openftv-pdp All interaction goes through APIs.
    D-10 Information security and privacy by design Base ◐ PR #242 (CA keys outside the runtime), PR #222, PR #220, REQ-69, REQ-66 The demo has mTLS over FSC, CA keys outside the application runtime, no per-party values in the register, and source metadata that fails closed. Open: there is no penetration test or audit (D-12), and the demo uses its own CA instead of PKIoverheid (Q-07).
    D-11 Least privilege Base ◐ REQ-48, REQ-81 The demo limits the fields per scope and takes the subject from the proof. Every rule names its services (REQ-97), and only the Inway reaches the source gateway. F-08 is closed: no source requires a certificate-bound token.
    D-12 Demonstrable security: audit and penetration testing Base ◐ policies/gbo (policy tests), etsi-ts-119478.yaml Policy unit tests and an ETSI conformance matrix with a check in CI. No penetration test or audit.
    D-13 Standardize where possible Base ◐ dvt0001.rego#L65 The scope convention bd:ib:<year> is ad hoc.
    D-14 Interoperability: semantic and technical alignment Base ◐ graphql-server The source schemas follow the gbo-semantiek v0.3 source profiles. There is no canonical semantic model.

    S04 Organization authentication and trust framework Base ◐ fsc-infra, autosign.rego#L171 A register admits organizations to the system, and the PDP decides on contracts (REQ-61, REQ-62).     S05 Authorization (PEP/PDP/PIP) Base ◐ engine.rego#L173 (regime), consent.rego#L268 (status), ftvgraphql.go The regime follows from the evidence (REQ-74, F-70). These RL items are guidelines: management stays with each bronhouder (Q-21). Open: validation before activation (F-52, RL-05), push distribution (F-51), and the policy version in the decision record (REQ-59).
    S07 Data access (source access API) Base ✓ REQ-17, REQ-97 GraphQL source access works for three sources. PSA S07 asks for pre-registered selective queries. The DvTP path lets the consumer send free queries within a field allowlist (Q-14).
    S08 OOTS adapter Hook — — Not in v1 (ADR-0020).
    S09 Logging, audit and traceability Base ◐ adl.go, ldv-logboek, request-flow.json The ADL is the audit source (REQ-71). Each system has an LDV logbook (REQ-72), and the trace comes from traceparent (REQ-55, F-67). Open: the BSN in the decision logs (REQ-60), and the record behind the Inway without a trace (#369). Also open: the read route to the consent log (Q-25, F-68), and the register of processing activities (Q-08).
    S10 Semantics and data catalogue Base ◐ gbo-source-metadata-v1.schema.json, source_metadata.go#L101 The source owns its service description on /.well-known/gbo, and GBO validates and activates it (F-57, REQ-64). In demo v0.9.0, this is built for EUDI and the ASIP. DvTP scopes come from rule files on the GBO side (F-17). There is no DCAT-AP-NL reference and no central findability. F-74 covers the DvTP catalogue per FR-32.
    S11 Attestation issuance (PuB-EAA / QEAA) EUDI ◐ eudi-issuance-server, eudi-adapter, eud0002.rego Issuance works for products of two sources (SL-43, REQ-57, REQ-58). Missing: a qualified seal and a trust list. F-80 and F-81 cover the regulation, F-82 covers change notification, and Q-30 covers the trust list.

    EUDI wallet and regulation (EUDI-1 to EUDI-11)¶

    The EUDI rows have five sources:

    • the GO sections on attestation issuance and on the verification service for QTSPs,
    • PSA S11,
    • eIDAS article 45e,
    • the implementing regulations (EU) 2025/1569 and 2026/1735,
    • ETSI TS 119 478.

    The EUDI-NN IDs belong to this matrix.

    ID Title Scope Status Evidence Notes
    EUDI-1 PuB-EAA provider and OpenID4VCI issuance EUDI ◐ REQ-58, REQ-64, REQ-77 Issuance works against mock trust (ADR-0018). PuB-EAA issuance falls under ETSI TS 119 471 and needs designation (F-81, Q-28).
    EUDI-2 Authentic Source Interface (QTSP verification, art. 45e) EUDI ◐ seal.go#L45, registration.go#L222 (re-check), asi0001.rego#L23, etsi-ts-119478.yaml, asi-route.md SL-28 is done. It built sealed verify and retrieve, its own authorization server, and the chain behind the ASIP over FSC. It also built discovery, a reference QTSP, and login with a DigiD mock and the NL Wallet. The GBO profile is in the ASI profile: REQ-83 to REQ-115. Open: the BSN in the token (#595, F-86), and an external QTSP (#594). The ASIP has no certification and seals with a development certificate.
    EUDI-3 PID presentation and signature verification EUDI ◐ client.go#L119 (ASI route) ASI route: the nl-wallet verifier verifies the PID against a fixed list of issuers (REQ-102). Issuance route: the issuance server verifies the PID. The callback to the adapter has no authentication, so nothing binds the BSN to the verified disclosure (#133, REQ-45, F-70).
    EUDI-4 Qualified seal and signing infrastructure (eIDAS2, ARF) EUDI ○ — The demo has no qualified seal. The ASIP seals with a development certificate (REQ-83). For more information, see FR-27.
    EUDI-5 Trusted lists and trust anchors EUDI ○ — The demo uses mock trust. The list on which PuB-EAA issuers appear is open (Q-30).
    EUDI-6 Attestation schemas and serialization (SD-JWT VC, mdoc) EUDI ◐ PR #224 (schemas published by the source, fixed per version) Each source publishes its schemas, and GBO validates and activates them (REQ-64). An integrity reference binds the schema to the credential. Q-20 (closed) covers the claim shape for related-person data.
    EUDI-7 Self-service access basis (subject = resource owner) EUDI ◐ engine.rego#L173, eud0001.rego The regime follows from the evidence (REQ-74). If a request carries no consent proof, it enters the PID regime. The PID regime has no positive evidence of its own (F-70, REQ-45).
    EUDI-8 Thin channel adapter / protocol translation EUDI ◐ source_metadata.go#L272 (query plan from the source description) The adapter cannot hold use-case knowledge: query, parameters, mapping, and offers come from the validated source description (REQ-64, REQ-44). It projects with gbo-simple-v1. If a result is ambiguous, the adapter fails closed (ADR-0017).
    EUDI-9 Issuer role and liability (PuB-EAA or QTSP) EUDI ○ — This is governance (Q-17). The reference QTSP issues a test attestation after an ASI verification (SL-28, part 13 of epic #336). Role and liability stay a governance matter.
    EUDI-10 Shared authorization service for both routes EUDI ◐ engine.rego#L173 One AuthZEN endpoint for DvTP, EUDI issuance and the ASI route. The regime follows from the evidence (REQ-74). Approval in the wallet is not a legal basis (F-83).
    EUDI-11 Related-person credential (subject of the claim is not the discloser) EUDI ◐ eud0002.rego, brp-graphql-server A surviving partner discloses his PID and gets the death certificate of the partner (SL-43). The source fixes the relation, and the PDP limits the output fields. REQ-57 prefers the relation as enforceable filters in the schema (#425). For more information, see F-47.

    Open decisions (B-01 to B-19)¶

    Source: the PSA decision register. The status shows how far the demo tries out or follows the preferred direction of the PSA. Governance and organization decisions that the demo cannot try out have the status "—".

    ID Title Scope Status Evidence Notes
    B-01 Governance of GBO agreements Base — — PSA direction: FDS as the base, with GDI and domain governance. This is governance. For more information, see Q-16.
    B-02 API profile for source access Base ◐ ftv-graphql-profile.md PSA direction: GraphQL, comply or explain. The demo uses GraphQL over FSC for all routes. The profile is a GBO proposal in the OpenFTV working group (#331). For more information, see Q-14.
    B-03 Service catalogue Base ◐ REQ-64 PSA direction: federated content, with a common profile for central findability. EUDI and ASI are federated. DvTP scopes are on the GBO side, without a ceiling per use case (#382, F-74). The demo has no central findability.
    B-04 PDP placement Base ◐ fsc-infra/docker-compose.yml#L773 PSA direction: several variants under one PEP-PDP interface. Demo shortcut: one shared PDP. A PDP per source works with bundles (SL-44). For more information, see Q-02 and Q-10.
    B-05 Policy governance Base ◐ RL-03 PSA direction: content ownership apart from technical management. The PAP splits read, write and publish (SL-44). Management stays with each bronhouder (Q-21).
    B-06 Consent in DvTP DvTP ◐ REQ-68 PSA direction: a central or nationally coherent facility, anchored in law, with an equivalent alternative. The demo has a central register and portal. Missing: the alternative (AV-15). For more information, see Q-05 and Q-13.
    B-07 Pseudonymous identity DvTP ◐ bsnk.go#L65, decryption.go#L76 The register holds no BSN (REQ-69). The demo follows the BSNk PP model on a mock (SL-51, REQ-80, BSNK-01 to BSNK-11, F-75). Open: recognition (Q-26), and a consumer pseudonym (Q-27, #478).
    B-08 Identity matching EUDI — — Not in v1: the PID carries the BSN, so no match is necessary (Q-18).
    B-09 Trust framework for private parties Base ◐ dvtp-onboarding-register PSA direction: FDS functions plus a legal and organizational framework. Demo: an admission register and FSC peers with certificates (SL-45, SL-49). The connection conditions are candidates for the framework. Q-07 and Q-22 give the answered direction. The PSA decision B-09 is open.
    B-10 Logging and citizen access Base ◐ REQ-55, REQ-71, REQ-72 PSA direction: logs stay decentral, correlation is federated. Open: the read route from ADL to LDV (Q-25) and the access model for the citizen (F-65, F-68).
    B-11 Semantic governance Base ○ — The mapping is per source, without shared concepts (F4, S10). For more information, see Q-11.
    B-12 OOTS function boundaries Hook — — Not in v1 (PAT-B).
    B-13 PuB-EAA issuance model EUDI ◐ REQ-58 The demo has a central issuance facility with a certificate set per source. Key management and seal are open (Q-17, #225). The issuer is the bronhouder or a designated body (F-81, Q-28).
    B-14 ASI provider EUDI ◐ see EUDI-2 The ASIP mock and the authorization server are two roles, each with its own keys. Neither is certified. Each source has one data service (REQ-94, F-89), and each data service has a discovery record (REQ-99, F-91). The interface and the seal are law from January 1, 2027 (F-80). Q-37 covers the role of GBO.
    B-15 Start of attestation issuance EUDI ◐ — PSA direction: several standardized start routes. The demo has one route: a QR code from the developer portal.
    B-16 GBO translation layer Base ○ — Not in the demo: all sources use GraphQL.
    B-17 Management of reference components Base — — Organization decision. The demo cannot try it out.
    B-18 Report of errors or suspected inaccuracies Base — — Not in v1. The PSA does not describe it in detail.
    B-19 Representation and authority credentials Base ◐ integrator.md First case: an integrator under FSC delegation. The decision uses the acting and the represented party (PR #464, F-73, REQ-106). Q-46 covers the integrator in the proof, and Q-73 covers citizen representation.
