    Requirements¶

    A requirement in this technical design is a testable demand on what GBO builds, or on the interfaces between GBO and other parties. It follows from the design (GO, PSA, FR-DvTP), or the GBO team derived it from building the demo. Each requirement states where it comes from.

    The arc42 sections explain the design, and the architecture decisions record the choices. A requirement states the need that a section or a decision serves. Each arc42 page and each ADR ends with a traceability footer. The footer lists the requirements that the page explains or depends on. The traceability pages link requirements to findings, open questions, and demo increments.

    When something is a requirement¶

    A REQ-NN counts as a requirement only with these four properties:

    1. Testable: MUST, MAY, or MUST NOT, with a result that you can observe.
    2. Sourced: it names the passage in the design that it follows from. For a requirement derived from the demo, the source is the principle or capability that it serves, with one sentence about the reason.
    3. Addressed: it is addressed to a component that GBO delivers, or to an interface agreement (see Addressee).
    4. A need: it describes the need and does not describe the chosen solution.

    The test for a derived requirement is one question: which principle or capability breaks without this requirement? If there is no answer, it is no requirement.

    What is not a requirement¶

    Three levels of items are no requirements, and each level lands in its own place:

    Level Example Where it lands
    Demo glue mocks, seeds, provisioning, the fake DigiD nowhere
    Implementation detail a switch, a design pattern, a library in the code
    Design decision never cache the status, or keep keys for at most five minutes an ADR, or a note on the requirement that it serves

    Need or decision: ask can another solution meet the same need? If yes, the need is the requirement, and the chosen solution is a design decision.

    When a design decision becomes an ADR: a design decision becomes an ADR only if all three conditions apply:

    • There were real alternatives.
    • Going back is expensive (an interface, a data model, or another party).
    • Someone outside the team must know about it or agree to it.

    If not, the decision is a note "design choice" on the requirement that it serves. Related choices go into one ADR. The ADRs are in Architecture decisions.

    Entry format¶

    Each requirement entry has this format:

    ## REQ-NN — Title as a statement {#req-nn}

> The [component] MUST [testable demand].

| Case | Outcome |        (optional: what must hold, with the deny reason)
|---|---|

- **Source**: design — PSA S04, FR-34 criterion 1
             or: derived — serves PSA S01: why, in one sentence
- **Addressee**: GBO-delivered component | interface agreement | guideline for source holders
- **Evidence**: demo issue or PR, with a permalink to the test or the code;
               or: not built — issue
- **Related**: links only (REQ, F, Q, ADR)
- **Notes**: only what a builder needs; an open point as a link to the Q
- **Status**: draft | ready for review | approved | covered | withdrawn

    The fields have these rules:

    • Source: the value is design if the design already states or sharpens the requirement. The value is derived if the requirement comes from the demo. PSA and GO links go to the published site. FR-DvTP criteria are named without a link until the FRs are public. The archived reference architecture (v0.6.2) is no longer a source. The PSA passage replaces it.
    • Evidence: the place where the demo tests the requirement: an issue or PR in gbo-demo, and a permalink to the test or the code. Later, test tags with coverage from CI will replace this field.
    • Related: only references that work as links.
    • Notes: limits, design choices, and open points. No history: the page describes the design as it is.

    Status¶

    An entry has one of these statuses:

    Status Meaning
    draft written by the analysis team
    ready for review meets this norm
    approved accepted in the review with the tech lead
    covered a test shows the requirement
    withdrawn an approved requirement that no longer applies. It stays, with the reason and the successor, because others can refer to it
    candidate a connection condition (AV) that is proposed and not set

    If a requirement was never approved and no longer holds, the GBO team removes it and does not withdraw it. Nobody uses its number again. For more information, see Removed numbers.

    Addressee: a MUST is only about what GBO builds¶

    The system is federative (Q-02), and P-10 puts the source holder (bronhouder) in control. So a requirement that prescribes how a source holder configures its own PDP, PAP, or policy engine is no requirement. Nobody can enforce it in practice. Each requirement names its addressee:

    • GBO-delivered component: software that GBO builds and delivers as a generic component or reference implementation. A MUST applies, because it is a demand on an artifact of GBO itself. Delivery does not mean operation: most of these components run at the source (behind the Inway: PEP and PDP, adapters, request mappers, gateways). The requirement binds the GBO build. It does not limit the freedom of a source to choose something else.
    • Interface agreement: behavior at the outside that every participant must deliver, because it follows from system or legal demands. For example, you can trace which policy version a decision used. A MUST applies, but only to the observable result. It never applies to the internal configuration or the product.
    • Guideline for source holders: the internal configuration at a source. At most SHOULD, with the reason, or a selection criterion for a product.

    Three other namespaces hold what is not a requirement on GBO:

    • RL-NN: guidelines for source holders, on Policy management. Matrix and findings can refer to them like a requirement, without the suggestion that they are one. Each guideline has a promotion rule: the open question that must be answered before it can become a requirement.
    • AV-NN: candidate connection conditions, obligations for other participants, on Connection conditions.
    • BSNK-NN: preconditions that BSNk PP, an external facility, imposes on GBO, on BSNk preconditions.

    If you write a requirement, do two checks:

    1. Does the MUST sentence name a product or an implementation form that GBO does not deliver? If so, reword the sentence to the role (PAP, PDP, management API), and change the addressee. The use of a product in the demo is a demo choice. It belongs in the evidence.
    2. Does the requirement assume that GBO runs something? That is almost never certain. It is open which facilities are really central (Q-10, Q-02). The demo runs everything in one stack, and that proves nothing about it. Write the requirement on the artifact or on the interface.

    Organization of the pages¶

    Topic pages are grouped by channel, as in the building block view: GBO Basis (needed for every channel), DvTP, and EUDI. A requirement that belongs to one channel only is on a topic page of that channel. If a requirement moves to another page, its number does not change.

    All requirements¶

    Every live number is in one of the following tables. The channel is GBO Basis (needed for every channel), DvTP, or EUDI. The source is design if the design already states the requirement, and derived if it comes from building the demo.
