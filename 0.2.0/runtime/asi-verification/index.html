    ASI verification: a QTSP verifies or retrieves an attribute¶

    A qualified trust service provider (QTSP) asks the Authentic Source Interface Provider (ASIP) to verify or retrieve attributes of a citizen at the authentic source. This exchange follows eIDAS Article 45e and ETSI TS 119 478, clause 6.1 (ADR-0037, GO: ASI provider). The citizen approves each request by logging in at the authorization server of the ASIP.

    The ASI route in gbo-demo v0.9.0 has four runs:

    1. Discovery and registration
    2. Authorization and login
    3. Verify through the chain
    4. Test statement to the wallet

    For the concepts, see these pages:

    • The components and the trust boundary: Level 2: ASI chain.
    • The profile per ETSI clause: ASI requirements.
    • The trust roles: ASI trust roles.
    • The source description: The asi capability.
    • What is real, stub, or interpretation in the demo: docs/asi-route.md.

    The demo runs one data service, brp, for the authentic source rvig (BRP mock). Its base URL is /brp/authsrc-api (ADR-0038, dataservices.json). The QTSP is the reference QTSP of the demo. It is not a real QTSP. The route runs only in the local stack (make demo-asi).

    Discovery and registration¶

    A QTSP finds the data service for an attribute without addresses in its configuration (REQ-99, REQ-100). The QTSP registers once per authorization server (REQ-88).

    sequenceDiagram autonumber box rgb(241,239,232) External roles participant Q as QTSP<br/>(qtsp-reference) participant DIP as Discover Interface<br/>(asi-discovery-stub) end box rgb(255,237,213) ASI provider participant ASIP as ASIP<br/>(asi-provider) participant AS as Authorization server<br/>(asi-authorization-server) end box rgb(237,233,254) Register participant REG as Register of relying parties<br/>(stub file) end Q->>DIP: GET /retrieve, queryType dataServices,<br/>attributeIdentifier, conformsTo DIP->>ASIP: GET /brp/dataservices ASIP-->>DIP: dataService records of the active description DIP-->>Q: Records: endpointURI, endpointDescription,<br/>provider, country Q->>Q: One data service for all attributes? Q->>ASIP: GET /brp/openapi.json ASIP-->>Q: Contract: servers, x-oauth-authorization-server Q->>AS: GET /.well-known/oauth-authorization-server AS-->>Q: Metadata: issuer, endpoints, jwks_uri Q->>Q: Metadata URL belongs to the issuer? Q->>AS: POST /register: redirect_uris, scope,<br/>software_statement with x5c and registryURI AS->>AS: Chain to a trust anchor, certificate valid,<br/>organizationIdentifier, iss, iat, exp AS->>REG: Look up registryURI REG-->>AS: Identifiers, entitlements, legal name AS-->>Q: 201: client_id, jwks with the certificate key Note over AS,REG: Every hour, for each registered client AS->>REG: Look up registryURI again AS->>AS: No QEAA_Provider: deactivate.<br/>Register unreachable: keep active.

    Each hop of discovery and registration carries the following data:

    # From → To Data Notes
    1 to 4 QTSP → Discover Interface → ASIP In: an attribute identifier. Out: one record per attribute and data service No personal data travels. The stub holds no records. It reads them per query from the ASIP and checks them against the ETSI schema (directory.go#L35-L40). The ASIP lists the attributes of the active source description. If no description is active, the ASIP answers 503 (handler.go#L139-L165).
    5 QTSP (internal) The records A token is for one data service. If no data service provides all attributes, the QTSP stops before the authorization server (qtsp.go#L124-L162, F-89).
    6 to 7 QTSP → ASIP The contract (ETSI Annex B OpenAPI) servers must equal the endpointURI. x-oauth-authorization-server is a GBO extension: ETSI requires the reference but gives no field (F-91, Q-39, E1).
    8 to 10 QTSP → authorization server RFC 8414 metadata The QTSP checks that the metadata URL is the RFC 8414 location for the issuer (qtsp.go#L190-L214).
    11 to 12 QTSP → authorization server RFC 7591 request with a software statement, sealed with the QTSP certificate (x5c, registryURI) No personal data travels. The certificate must chain to a trust anchor and carry an organizationIdentifier. In the demo, the certificate comes from the development reader CA. It is not an access certificate per ETSI TS 119 411-8 (F-85).
    13 to 15 Authorization server ↔ register registryURI. Out: identifiers, entitlements, legal name The entry must carry QEAA_Provider and the organizationIdentifier of the certificate (registration.go#L199-L215). It is open which identifier links the two (Q-35). The client key is the certificate key. The authorization server keeps clients in memory.
    16 to 17 Authorization server ↔ register The same lookup The re-check runs every AZSP_ENTITLEMENT_RECHECK_INTERVAL (1 h) (REQ-89, registration.go#L221-L245). If the register is unreachable, the client stays active (Q-34). Tokens already issued stay valid (Q-41).

    Authorization and login¶

    The citizen starts at the QTSP and logs in there first. The QTSP then sends the browser to the authorization server. One request page shows who asks what at which source (REQ-91). The citizen approves by logging in, or refuses (REQ-90). The diagram shows three alternatives: the cross-device wallet login, the DigiD mock, and a refusal.

    sequenceDiagram autonumber box rgb(221,235,247) Citizen actor C as Citizen<br/>(browser) end box rgb(241,239,232) QTSP participant Q as QTSP end box rgb(255,237,213) ASI provider participant AS as Authorization server participant V as Wallet verifier<br/>(nl-wallet) end box rgb(241,239,232) Wallet participant W as NL Wallet<br/>(phone) end C->>Q: Log in at the QTSP: NL Wallet without BSN,<br/>or test data C->>Q: POST /start: product and values Q-->>C: 302 to /authorize: code, PKCE S256, state,<br/>scope, resource, authorization_details C->>AS: GET /authorize AS-->>C: Request page and transaction cookie C->>AS: POST /authorize/decision alt NL Wallet, cross-device AS->>V: POST /disclosure/sessions: asi-login,<br/>PID with five claims V-->>AS: session_token, kept with the transaction AS-->>C: Wallet page with QR code, refreshes itself W->>V: Fetch the request, signed with the<br/>reader certificate of asi-login W->>V: Presentation: PID as SD-JWT VC V->>V: Issuer signature, trusted issuer,<br/>wallet binding C->>AS: GET /authorize/wallet: status DONE AS->>V: GET disclosed attributes, API key V-->>AS: bsn, family_name, given_name,<br/>birthdate, nationalities else DigiD mock AS-->>C: DigiD mock page C->>AS: POST /authorize/digid: BSN as password else Refuse AS-->>C: 302 to redirect_uri: error access_denied end AS-->>C: 302 to redirect_uri: code and state C->>Q: GET /callback: code, state Q->>AS: POST /token: code, code_verifier,<br/>client_assertion, DPoP proof AS-->>Q: Access token, at+jwt, 10 min

    Each hop of authorization and login carries the following data:

    # From → To Data Notes
    1 Citizen → QTSP name, birth date, nationalities (no BSN) The QTSP uses use case qtsp-login on the same verifier, with its own reader certificate. This shared verifier is a demo shortcut. The test-data login is a stub. The QTSP keeps the login in memory for 30 minutes.
    2 to 3 Citizen → QTSP → browser The product and the values to check (address) The redirect carries PKCE S256, state, the operation as scope, resource = the endpointURI, and authorization_details with the attribute identifiers (REQ-103, ADR-0042). The values stay at the QTSP.
    4 to 5 Browser → authorization server The authorization request. Out: the request page If resource does not name exactly one data service, the answer is invalid_target (REQ-95). The page names the QTSP by its legal name from the register, the operation, the source, and the attributes. The transaction lives 5 minutes and is used once. A cookie binds the transaction to the browser.
    6 Browser → authorization server The choice: wallet, digid, or deny The choice of a means starts the approval. The code comes only after a successful login.
    7 to 9 Authorization server → verifier → browser DCQL: urn:eudi:pid:nl:1 with bsn, family_name, given_name, birthdate, nationalities The authorization server keeps the session with the transaction and never takes one from the browser (provision.go#L33-L49).
    10 to 12 Wallet ↔ verifier PID with the BSN The reader certificate names the authorization server. It does not name the QTSP. Any phone can scan the QR code (F-93). The verifier verifies the issuer signature, the trusted issuer, and the wallet binding. The trusted issuers come from a fixed list. They do not come from a trusted list (REQ-102, Q-36).
    13 to 15 Authorization server ↔ verifier BSN, names, birth date, nationalities Only a PID of the right type with a BSN identifies the citizen. The NL PID has no place of birth (F-94).
    16 to 17 Browser → DigiD mock BSN The DigiD mock is a stub. It checks only for nine digits and gives only the BSN (F-88).
    18 Authorization server → browser error=access_denied No login takes place, and the source gets no request.
    19 to 20 Browser → QTSP code, state The code is single use and valid for 60 s. Before the QTSP asks for a token, it checks its session and state.
    21 QTSP → authorization server POST /token: code, code_verifier, private_key_jwt client assertion, DPoP proof From each pair of mechanisms that ETSI offers, the demo uses one: private_key_jwt and DPoP. The demo uses no mTLS and no PAR (F-84, Q-66).
    22 Authorization server → QTSP RFC 9068 access token, ES256: aud = data service, scope, authorization_details, cnf.jkt, opaque sub, BSN claim, acr/amr, PID claims (wallet only) The QTSP can read the BSN in the token (F-86, E7, #595). The token carries the means used (REQ-86, tokens.go#L53-L85).

    Same-device wallet login¶

    If the browser and the wallet are on one phone, a button opens the wallet. The wallet returns the browser with a nonce (#548, PR #573). This flow needs an HTTPS issuer, because nl-wallet accepts only an HTTPS return URL. Over local HTTP, the button is disabled, and only the QR code works. A run on a real phone waits for the simulation environment (#596, #594).

    sequenceDiagram autonumber box rgb(221,235,247) Citizen actor C as Citizen<br/>(browser on the phone) end box rgb(255,237,213) ASI provider participant AS as Authorization server participant V as Wallet verifier end box rgb(241,239,232) Wallet participant W as NL Wallet<br/>(same phone) end C->>AS: POST /authorize/decision: wallet AS->>V: POST /disclosure/sessions with a return<br/>template to /authorize/wallet/return V-->>AS: session_token, kept with the transaction AS-->>C: Button Open NL Wallet and QR code C->>W: Universal link opens the wallet W->>V: Fetch the request, presentation W-->>C: Back to the website: return URL with nonce C->>AS: GET /authorize/wallet/return:<br/>transaction, session_token, nonce AS->>AS: Session of this transaction<br/>in this browser? AS->>V: GET disclosed attributes with the nonce V-->>AS: PID, only for the right nonce AS-->>C: 302 to redirect_uri: code and state

    These hops carry the data that is specific to the same-device login:

    # From → To Data Notes
    2 Authorization server → verifier The return template The verifier returns only after a same-device session (session_type_return_url = "same_device", only for asi-login).
    7 to 9 Wallet → browser → authorization server transaction, session_token, nonce The authorization server refuses another browser or another session before it calls the verifier. The browser also comes back after a refusal in the wallet (identification.go#L322-L356).
    10 to 11 Authorization server ↔ verifier nonce. Out: PID with the BSN The nonce binds the disclosure to the browser that the wallet returned. Another phone cannot finish this session (F-93).

    Verify through the chain¶

    The QTSP calls the ASIP with the token. The ASIP verifies the token, takes the BSN from it, and calls the source once, through its own FSC Outway. The generic GBO chain starts behind the ASIP (F-87).

    sequenceDiagram autonumber box rgb(241,239,232) QTSP participant Q as QTSP end box rgb(255,237,213) ASI provider participant ASIP as ASIP<br/>(data service brp) participant AS as Authorization server end box rgb(220,252,231) GBO Basis participant OW as asip-outway<br/>(peer …1200) participant IW as bd-inway<br/>(PEP, peer …0200) participant PDP as OpenFTV PDP<br/>(ASI0001) participant GW as Source gateway<br/>(brp-sidecar) end box rgb(221,235,247) Source participant SRC as BRP mock<br/>(brp-graphql-server) end Q->>ASIP: POST /brp/authsrc-api/verify: DPoP token,<br/>DPoP proof, traceparent, attributes ASIP->>AS: Metadata and JWKS, once, cached AS-->>ASIP: Signing keys ASIP->>ASIP: Token, proof and scope.<br/>BSN from the token. ASIP->>ASIP: Contract schema, approved attributes,<br/>mandate, attributes described ASIP->>ASIP: One query from the active<br/>description, only the needed fields ASIP->>OW: POST /brp/graphql: query, BSN as variable,<br/>Fsc-Transaction-Id, traceparent OW->>IW: mTLS, Fsc-Authorization, same body IW->>PDP: POST /authzen/v1/evaluation with the body PDP-->>IW: Allow per field, ADL record IW->>GW: Query GW->>SRC: Query unchanged, no consent token SRC-->>ASIP: Fields of the person, or no person ASIP->>ASIP: Build the attributes and compare ASIP-->>Q: 200: attributeVerificationResults,<br/>X-JWS-Signature Q->>Q: Seal valid? Else not accepted.

    Each hop of the verification carries the following data:

    # From → To Data Notes
    1 QTSP → ASIP Authorization: DPoP <token>, DPoP proof with ath, attribute values to check The values are personal data that the QTSP already has. insufficient_scope and every other token error give 401, as ETSI lists.
    2 to 3 ASIP → authorization server jwks_uri from the metadata If the kid is unknown, the ASIP fetches the keys again. If the keys are not available, the ASIP answers 503 (REQ-87).
    4 ASIP (internal) Token, proof. Out: the BSN The ASIP first verifies the token: signature, issuer, aud, expiry, DPoP binding and replay, and scope (handler.go#L222-L258). The BSN comes only from the token. No log line holds the BSN.
    5 ASIP (internal) The request Schema against the contract: 400. Attributes outside authorization_details: 401. mandate: 501. An attribute the source does not describe: 404 (handler.go#L260-L356, service.go#L129-L139).
    6 ASIP (internal) The asi description from the active release The ASIP reads the active release every 5 s with the reader role. It derives one query with only the fields of the requested attributes (REQ-92, ADR-0039).
    7 ASIP → asip-outway POST /brp/graphql (grant link /brp): {query, variables: {bsn}} with the BSN, Fsc-Transaction-Id, traceparent One FSC transaction per request. The span names the source, the transaction ID and the attribute identifiers, never the BSN or a value (source.go#L75-L104, REQ-55).
    8 asip-outway → bd-inway FSC, mTLS, with the body and the BSN The hop uses the contract of the ASIP peer …1200 for service brp on …0200 (FSC peers).
    9 to 10 bd-inway ↔ PDP AuthZEN: actor …1200, service brp, the query with the BSN ASI0001 grants the ASIP peer the BRP fields behind the attributes, on brp only. It does not check the token or the QTSP (asi0001.rego#L1-L72, REQ-97). The PDP never sees the QTSP or the citizen. The ADL holds the BSN (REQ-60, ADR-0043).
    11 to 12 bd-inway → gateway → BRP mock The judged query If the query has no consent token, the gateway passes it through. The BRP logs its own processing. In demo v0.9.0, the ASIP writes no LDV records.
    13 BRP mock → ASIP fields of the person, or null The answer goes back through the same FSC chain.
    14 ASIP (internal) Fields. Out: a result per attribute pointer, join, const, and each build the attribute from the fields. The result is Match, MatchWithVariation, NoMatch, or Unknown. Unknown means only that the source holds no value (REQ-84). Fuzzy matching applies only to strings without a format (REQ-113).
    15 ASIP → QTSP results, provider, authenticSource (legal name from the description), header X-JWS-Signature A verify response holds no source value (REQ-85). One authentic source per response (REQ-94). The seal is a detached JWS, ES256, with x5c, over the exact body. The ASIP does not seal errors (REQ-83, ADR-0041, handler.go#L402-L417).
    16 QTSP (internal) The seal The chain must lead to QTSP_SEAL_TRUST_ANCHORS. If it does not, the QTSP does not accept the result.

    The retrieve operation runs the same way at POST /brp/authsrc-api/retrieve with scope retrieve. The request names attribute identifiers, without values. The sealed 200 carries the values of every requested attribute. If the source holds no value for one of them, the answer is 404. Retrieve gives no partial result (REQ-101).

    Test statement to the wallet¶

    After an accepted result, the reference QTSP issues a test statement to the wallet of the citizen who logged in at the QTSP. The QTSP uses the central issuance server of the EUDI route, with its own use case and its own certificates (qtsp_issuance.go#L19-L27, EUDI issuance).

    sequenceDiagram autonumber box rgb(221,235,247) Citizen actor C as Citizen<br/>(browser) end box rgb(241,239,232) QTSP participant Q as QTSP end box rgb(255,237,213) EUDI participant IS as Issuance server<br/>(nl-wallet) end box rgb(241,239,232) Wallet participant W as NL Wallet<br/>(phone) end Q->>Q: Accepted result: pending statement<br/>with the login identity Q-->>C: Result page with a QR code<br/>for use case qtsp-attestation W->>IS: Fetch the request, signed with<br/>the reader certificate of the QTSP W->>IS: PID: family_name, given_name,<br/>birthdate, nationalities, no BSN IS->>Q: Callback over internal HTTPS,<br/>secret path, the shared attributes Q->>Q: Same as the login identity? Q-->>IS: Statement: subject, outcome per attribute,<br/>source, date, test and not qualified IS-->>W: SD-JWT VC over OpenID4VCI, signed<br/>with the issuer certificate of the QTSP

    Each hop of the test statement carries the following data:

    # From → To Data Notes
    1 to 2 QTSP → browser The result and a fixed link per use case This hop occurs only after Match, MatchWithVariation, or a retrieved value. The pending statement lives 10 minutes in memory and is used once. A later request of the same citizen replaces it.
    3 to 4 Wallet → issuance server PID without the BSN A QTSP is not allowed to process the BSN.
    5 Issuance server → QTSP name, birth date, nationalities The QTSP gets no session, only the shared attributes. The callback uses a secret path over CA-pinned HTTPS, without client authentication (qtsp_issuance.go#L134-L152).
    6 QTSP (internal) The identity The link to the login uses only these personal data. This link is a demo binding and does not check a unique identity (F-93).
    7 to 8 QTSP → issuance server → wallet statement The statement is valid for 30 days, has attestation_qualification = "EAA", and carries a clear test marking. It is not a QEAA. For MatchWithVariation, the statement records the value that the QTSP sent. It does not record a source value.

    Main observations¶

    The ASI route in gbo-demo v0.9.0 has these properties and gaps:

    • The QTSP is outside FSC. Its admission is a certificate and a register entitlement at the authorization server. The source and the PDP see only the ASIP peer …1200. The ASIP passes nothing about the QTSP into the chain (F-87, Trust boundary).
    • Two logins, no link. The citizen logs in at the QTSP and at the authorization server. Nothing proves that it is the same person. In the cross-device route, another phone can scan the QR code (F-93, Q-40, E6).
    • The BSN travels in two places where it is not needed. The QTSP can read the BSN in the token (F-86, #595). The PDP input and the ADL also hold the BSN (REQ-60, ADR-0043).
    • Approval is a login, not a consent. The citizen approves one request. The demo stores no approval, and the citizen cannot revoke one (REQ-90, Wallet approval is not a legal basis).
    • One token per source. A QTSP that needs attributes of two sources authorizes twice. The citizen sees each source by name (ADR-0038, F-89, E3).
    • Per-attribute binding is optional. If the request has no authorization_details, the token binds only per operation, as in ETSI. A configuration option makes the detail required (ADR-0042, F-95, Q-33).
    • No value with a variation. MatchWithVariation returns no value. The conformance matrix records that row as failing (F-92, Q-29, E2).
    • The seal format is a GBO choice. ETSI defines no seal format (Q-32, E4). The demo seals with a development certificate.
    • Identification data is incomplete. The NL PID has no place of birth. The DigiD mock gives only the BSN (F-88, F-94, Q-36).

    Not built in demo v0.9.0¶

    Demo v0.9.0 does not build these parts of the ASI route:

    • A resource list from the source descriptions. The authorization server takes its resource list from AZSP_RESOURCES. The rest of the asi capability is built (#592, Q-38).
    • A deployment in the simulation environment, and a connection of an external QTSP (#594).
    • Protection of the BSN in the access token (#595, F-86).
    • A same-device wallet login on a real phone. It is built and tested, and waits for #594 (#596).
    • iss in the authorization response, RFC 9207 (F-96, E9). The effect of a withdrawn entitlement on issued tokens (Q-41, E10).
    • LDV records by the ASIP and the authorization server (REQ-72).
    • Clause 6.2 (ISO 15000) and deferred answers (REQ-112, Q-64). Requests on behalf of another person (Q-65).
    • A production register, access certificates per ETSI TS 119 411-8, real DigiD, and a qualified seal certificate (F-80, F-85, Q-28, Q-37).
    • Registration of the data services in the Discover Interface (Q-31, Q-67).
