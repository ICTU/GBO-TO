    Admission and activation¶

    Two management-plane scenarios come before the first request:

    1. Contract admission: a party asks for an FSC contract. The FSC Manager of the provider asks the PDP whether that party is admitted.
    2. Source activation: the operator of a GBO component takes a source into use. The component fetches the service description of the source, validates it, and activates it as an immutable release.

    Both scenarios carry no citizen data. They share one principle: a valid contract is necessary, but it is not enough. Admission comes from a register and does not follow from the contract (REQ-61). Activation is an explicit management action and does not follow from the contract either (REQ-65).

    For the concepts, see Authorization: admission and contract acceptance and Source onboarding. The decisions are ADR-0015 and ADR-0016.

    Scenario 1: contract admission¶

    A consumer, an integrator, or a GBO component (the issuance facility, the ASIP, the PDP itself) wants to connect to an FSC service of a source holder. The party creates a contract proposal in its own FSC Manager. The FSC Manager of the provider does not sign on a flag. It sends every proposal to the OpenFTV PDP as an AuthZEN evaluation and signs only on allow (fsc-infra/docker-compose.yml#L701-L702). The FSC Managers of the BRP peer and the consent register peer use the same policy (#L892-L893, #L1079-L1080).

    Data per hop¶

    Each hop of contract admission carries the following data:

    # From → to Interface Data Notes
    1 Administrator → register Register UI (localhost:9415), CSRF-protected forms FSC Peer ID (20 characters), display name, active, Peer IDs of the admitted source holders The register has no accounts. Anyone who reaches the UI locally is administrator (README). Integrations (acts_for) and technical participants are part of the deployment configuration. The UI does not manage them
    2 to 3 PDP → register GET /internal/openftv/participants (handler.go#L63), interval 5 s, timeout 2 s data.entities.dvtp_participant, keyed by Peer ID: name, active, allowed_source_peer_ids, acts_for (dvtp-onboarding.yaml) The pull uses a network that only the register and the PDP share. Every entry carries acts_for. If the party acts for nobody, acts_for is empty. As a result, a withdrawn mandate replaces the old entity
    4 Consumer → own FSC Manager POST /v1/contracts, internal API, mTLS (seed-bri-connection-hv.sh#L113-L135) Contract content: grant (type and service), validity, the peers FSC grants carry no properties (ADR-0031)
    5 Consumer Manager → provider Manager FSC Manager interface, mTLS with the organization certificate (demo CA) Signed contract proposal The contract hash identifies the proposal. A new submission is a new proposal with a new hash
    6 Provider Manager → PDP AuthZEN, https://openftv-pdp:8443/authzen/v1, the Manager pins the PDP CA subject (self_peer_id, peer_ids), action autosign_contract, resource (contract hash, grant_types), context.doelbinding = auto_sign_contract (autosign.rego#L12-L15) The input has no service name and no delegation direction. The PDP judges who connects. It does not judge to which service (F-56)
    7 to 8 PDP Package doelbinding.auto_sign_contract, separate from the request policy (REQ-62) Decision record in the ADL, next to the request decisions The doelbinding selects the package. A renamed package resolves to nothing (autosign.rego#L8-L10)
    9 to 11 PDP → provider Manager → consumer Manager AuthZEN response, then FSC signature Allow: FSC_AUTOSIGN_ADMITTED_PARTY, counterparties, source Peer ID. Deny: first failing code, counterparties, grant types (autosign.rego#L184-L202) The response holds only Peer IDs and no personal data

    Ordered refusal codes¶

    The policy runs eight checks in a fixed order. The first check that fails names the refusal (autosign.rego#L165-L175). Each check defaults to false, so malformed input leads to a refusal instead of an undefined check. The policy refuses a contract for one of eight reasons, in this order:

    # Code Refuses when Tests (v0.9.0)
    1 NOT_AN_AUTOSIGN_REQUEST The action is not autosign_contract, the resource is not a contract, or attributes are missing autosign_test.rego#L223, #L230, #L239
    2 GRANT_TYPE_NOT_ALLOWED The grants are not all type 2 (service connection) and not all type 3 (delegated service connection): a publication, a mix, or no grant #L149, #L205, #L209, #L213
    3 NO_COUNTERPARTY The contract names no party other than the provider #L219
    4 ADMISSION_REGISTER_UNAVAILABLE The PIP pull supplied no register #L86, #L91
    5 PARTY_NOT_IN_REGISTRY A counterparty is not in the register. This also applies when the register is empty #L130, #L96, #L190
    6 PARTY_NOT_ACTIVE A counterparty is suspended (active is not true) #L138, #L185, #L195
    7 SOURCE_NOT_ALLOWED A counterparty is not admitted for the Peer ID of this source #L109, #L113
    8 DELEGATION_NOT_REGISTERED The contract has a delegated grant, but no integration between the two counterparties is registered #L176, #L180, #L201

    The tests #L74, #L117, and #L171 cover the allow paths. If the policy refuses one party among several, it refuses the whole contract (#L143).

    A refusal leaves the proposal at proposed. The party can correct its admission and submit again. The new submission gets a new assessment (REQ-63). This behavior is product behavior of the FSC Manager. No automated test covers it. If a setup configures an automatic refusal, the setup breaks the requirement.

    Delegated grant (integrator)¶

    An integrator connects on behalf of a consumer (the represented party). The integrator uses one contract that holds a delegated service connection grant (type 3). The contract has three signatures (seed-bri-delegation-int.sh#L1-L17):

    sequenceDiagram autonumber box rgb(220,252,231) GBO Basis: FSC and PDP participant IM as FSC Manager<br/>of the integrator participant DM as FSC Manager<br/>of the represented party participant PM as FSC Manager<br/>of the provider participant PDP as OpenFTV PDP end IM->>IM: Create contract: delegated grant,<br/>integrator, represented party, service IM->>DM: Contract proposal DM->>DM: Accept (operator action) IM->>PM: Contract proposal PM->>PDP: AuthZEN evaluation, grant_types [3] Note over PDP: Checks 1–7 for both counterparties,<br/>then check 8: one acts_for the other PDP-->>PM: Allow, or DELEGATION_NOT_REGISTERED PM-->>IM: Countersignature: contract valid

    Each hop of the delegated grant carries the following data:

    # Data Notes
    1 to 2 Delegated grant with the Peer IDs of the integrator, the represented party, and the provider The FSC Manager of the represented party has no autosign. In the demo, the seed script accepts on its behalf. The script does what the operator does in the Controller UI (#L147-L167)
    4 to 6 peer_ids with the two counterparties, grant_types [3] The integrator must be admitted in its own right. A mandate does not replace the admission of either party

    The contract check admits the pair of counterparties. It does not check the direction (autosign.rego#L119-L139). The input does not say which party delegates. The check refuses a third counterparty. A contract that is signed the wrong way round passes this check, but the request policy denies it on every call.

    At request time, the provider Manager puts the represented party in the act claim of the access token. The engine then requires a mandate for the represented party and for the granting rule (engine.rego#L246-L267, ADR-0034). The engine decides as follows:

    Situation at request time Code Tests (v0.9.0)
    Registered integrator, mandate for the represented party and the rule allow engine_test.rego#L613
    No mandate for the represented party or the rule INTEGRATOR_NOT_REGISTERED #L621
    The integrator is suspended INTEGRATOR_NOT_REGISTERED #L706
    The register is missing from the PDP data INTEGRATOR_REGISTER_UNAVAILABLE in the trace, request code PIP_UNAVAILABLE. The consumer sees ACCESS_DENIED #L631

    The register attaches the mandates to the entry of the integrator (service_test.go#L245). The consent binds the represented party. It does not bind the integrator (REQ-106). For the DvTP query with an integrator, see DvTP query.

    Register missing against register empty¶

    The PDP data can be in two states that look the same but have a different meaning (autosign.rego#L43-L59, PR #579):

    PDP data Meaning Code
    No data.entities, or no dvtp_participant document The PIP pull supplied no register: an outage or a wrong mapping ADMISSION_REGISTER_UNAVAILABLE
    dvtp_participant is {} The register is available and admits nobody PARTY_NOT_IN_REGISTRY

    Both states lead to a refusal. The two codes tell the operator whether the pull or the admission needs a repair. The readiness script of the demo waits for the first successful pull before it seeds contracts (wait-openftv-admission.sh).

    The OpenFTV pull adds and replaces entities. If an entity disappears from a later response, the pull does not remove it. For this reason, the register deactivates a participant and never deletes it. A deleted record leaves the old admission in the PDP (REQ-61).

    Main observations¶

    Contract admission in gbo-demo v0.9.0 has these properties and gaps:

    • Admission is register data (F-55). No policy rule holds the admission. Adding, suspending, or withdrawing a party changes register data. The PDP sees the change within one pull interval of 5 s, without a policy change or a restart.
    • Contract and request rules are separate (REQ-62). The two rule sets share no rules and no reason codes. They do share one policy set and one availability object. As a result, one broken module stops both (F-52).
    • A suspended consumer keeps its access. A suspension stops only new contracts. At request time, the policy checks the status of an integrator. It does not check the status of a direct consumer. A suspended consumer with an existing contract can still request data, also with a valid consent (REQ-110, Q-53).
    • Changes are not traceable. The register has no accounts and no change log (REQ-123). The task to run the register is assigned to the management organization (Q-22). It is open who builds the facility (Q-74).
    • The register key is the FSC Peer ID. It is open whether policy can read the Peer ID as the OIN of the consumer (Q-68).

    Scenario 2: source activation¶

    For each source, the issuance facility and the ASIP need to know the data service, the query, the mapping, and the offer. The source publishes that description itself (REQ-64, F-57). The source reconciler of the EUDI adapter fetches the description, validates it, and writes it to the Source Registry. The runtime readers read only activated releases.

    First, the metadata contract and the data contract of the source must be valid. They pass contract admission like every other contract, because the issuance facility is a technical participant in the admission register.

    Each hop of source activation carries the following data:

    2 to 4 Operator → store → reconciler Public certificate store (--certificate-store=public-filesystem) Issuer, reader and status-list leaf certificates of the source The reconciler gets only public leaves. Only the issuance init container gets the private keys (REQ-58)

    7 to 9 Reconciler → Outway → source GET /.well-known/gbo with Fsc-Grant-Hash and If-None-Match Source metadata document (gbo-source-metadata-v1, version 1.0 or 1.1), ETag The PDP of the source allows only known peers, on the metadata services, on exactly this path (authz.rego#L14-L36).     10 Reconciler Validation (service.go#L399-L416) Schema, source_oin against the certificate, version, validity window, one read operation, mapping, offers, claims, the asi capability The data service that the document names must have a valid data contract
    11 Reconciler → registry Writer role Candidate per source, with state The registry refuses private key material

    For the document structure, the transports, and the release readers, see Source onboarding.

    Failure per source¶

    A source that fails gets the state stale or blocked. The other sources keep their state (REQ-66). For the reason codes, see service.go#L141-L152. Source activation handles each failure as follows:

    Main observations¶

    Source activation in gbo-demo v0.9.0 has these properties and gaps:

    • A valid contract is not activation (F-58). The source file is the management action. Transport and mandate are two decisions with two owners. Two parts are not built: the rule for who can take the action, and the way GBO records the admission decision. These parts are PSA B-09 in the besluitregister and REQ-123.
    • The source owns its description (F-57). GBO validates and activates the description. Its origin is the authenticated FSC transport plus the OIN from the certificate. The document itself has no signature. The file transport is a visible, temporary exception for a source without an endpoint. The demo does not record the agreement of the bronhouder (F-71, AV-08).
    • Releases have a full lifecycle (F-59). The lifecycle has validation before activation, bounded staleness, atomic promotion, and rollback. Policy bundles do not have this lifecycle. For a comparison, see Policy distribution.
    • Isolation is incomplete. One failing source freezes new releases for all sources, and the offer list fails for all sources at the same time (#606).
    • DvTP is not covered. For DvTP, the GBO rules hold the offer of a source. A publication of the source does not hold it (REQ-64). The question of how a source connects to the ASIP is partly answered (Q-38).
