    Authentic Source Interface requirements¶

    In the Authentic Source Interface (ASI) route, a qualified trust service provider (QTSP) verifies or retrieves attributes of a citizen at an authentic source. The QTSP does this at the request of that citizen. eIDAS article 45e gives the QTSP this right. The Authentic Source Interface Provider (ASIP) offers the interface. Its authorization server admits QTSPs and lets the citizen approve each request.

    The interface follows ETSI TS 119 478 V1.1.1, clause 6.1. Article 9 of Implementing Regulation (EU) 2025/1569 and Annex IV of Implementing Regulation (EU) 2026/1735 make clause 6.1.1 the legal interface for verification. Annex IV and the seal obligation of article 9(4) apply from January 1, 2027.

    The requirements on the ASIP and its authorization server cover these topics:

    • the verify and retrieve interface
    • the seal
    • the authorization server
    • the admission of QTSPs
    • the request page with citizen identification
    • the chain behind the ASIP, with one data service per source
    • discovery

    F-80 describes the legal frame. F-84 to F-89 describe the open design choices.

    Evidence links to gbo-demo point at two versions. A link at v0.9.0 shows the code of demo v0.9.0. A link at commit 819f3eb shows the code at the time of the review of the requirement. Use that link as historical evidence, because the file changed or moved after that commit.

    GBO profile on ETSI TS 119 478¶

    The specification for a Dutch ASIP is ETSI TS 119 478 V1.1.1, as Annex IV of Implementing Regulation (EU) 2026/1735 adapts it (Implementing Regulation 2025/1569, article 9(2a)). The profile does not repeat that text. For each clause, the profile records two things:

    • what GBO chooses, adds, or interprets on top of ETSI
    • where that choice is recorded: in a requirement on this page, an open question, or a finding

    A requirement that the profile does not name follows ETSI unchanged.

    The profile is for the build of the ASIP and its authorization server. That build does not reuse the code of the demo ASIP. The content for each requirement comes from two documents of the demo: the conformance matrix (etsi-ts-119478.yaml) and the documentation of the ASI route (asi-route.md). If nobody decided on a choice of the demo, the profile records it as an open question and does not make it a requirement.

    • Source: design. The source is the line on ETSI TS 119 478 in "Afspraken en standaarden" of PSA S11. The profile fills the open point "PubEAA-/ASI-profielen" from the summary of S11. Matters about the ASI provider and its conditions belong to PSA open decision B-14.

    Categories¶

    The profile puts each GBO choice in one of eight categories:

    Code Meaning
    K a choice where ETSI leaves room
    N not applicable because of a GBO choice
    R requirements on a role outside the ASIP and its authorization server (DIP, TSP)
    A an addition: GBO requires something that ETSI does not specify
    I an interpretation, or a conflict in the text
    X applies, but depends on an external facility
    O applies to the operator and not to the software
    open no decision

    External dependencies¶

    Some parts are a stub in the demo. For the build, each of these parts is a facility that must come from outside. They are not requirements on the ASIP. The profile needs these external facilities to apply in full:

    • the register of relying parties, and the API to look up the entitlement of a QTSP (F-85)
    • access certificates for QTSPs according to ETSI TS 119 411-8 (Q-35)
    • a qualified seal certificate for the ASIP (Q-17)
    • DigiD or another identification means next to the EUDI wallet (Q-36)
    • the EU catalogue of attributes, with IDs and value schemas (Q-38)

    REQ-83: Every ASIP verification result is sealed¶

    The ASIP MUST seal every successful response to verify and to retrieve. With only the received response and the trusted lists, the QTSP can then establish that the response comes unchanged from this ASIP. The seal MUST cover the response exactly and carry the certificate chain. The seal MUST be at least an advanced electronic seal. This seal MUST be based on a qualified seal certificate of the responsible public sector body or of the designated intermediary.

    Case Outcome
    verify, 200 sealed (code)
    retrieve, 200 sealed (code)
    error response (400, 401, 404, 500, 501, 503) not sealed (code, design choice)

    Source, evidence and notes
    • Source: design for verify, and derived for retrieve. The requirement has these sources:
      • Article 9(4) of Implementing Regulation (EU) 2025/1569. Article 1(3)(b) of Implementing Regulation (EU) 2026/1735 replaces it from January 1, 2027 ("the verification result shall be signed or sealed … using at least … an advanced electronic seal based on a qualified certificate").
      • PSA S11 ("ETSI-profielen voor gekwalificeerde zegels").
      • For retrieve, the requirement serves PSA S11. A QTSP can put a retrieved value in a qualified attestation. It must then show in the same way that the value comes from the source.
    • Addressee: GBO-delivered component: the ASIP. Interface agreement: the form of the seal, for every ASIP.
    • Evidence: ICTU/GBO-demo#498, PR #499. Code and tests:
      • The seal is in seal.go#L18-L57.

      • The header is an addition to the contract, in completions.json#L25-L33.
      • The tests are in handler_test.go#L240-L254, #L310-L312, and contract_test.go#L120-L121.

    • Notes:
      • The seal format is a design choice. It is a detached JWS (RFC 7515, Annex F) over the exact body, in the header X-JWS-Signature. It uses ES256 and carries the chain in x5c.
      • The body stays plain JSON, as the ETSI OpenAPI prescribes.
      • ETSI TS 119 478 defines no seal on the response. The format must be the same for all ASIPs (Q-32, E4).
      • An error response is not a verification result, so it gets no seal.
      • The demo seals with a development certificate. Who holds the qualified seal certificate is Q-17. Who the intermediary is, is Q-28.

    REQ-84: Unknown only means the source has no (complete) value¶

    If the source has no value, or no complete value, for this citizen, the ASIP MUST answer an attribute or fragment with Unknown. It MUST NOT give NoMatch in that case. An attribute that the data service does not deliver MUST get 404 (REQ-94) and MUST NOT get Unknown. A source that does not answer MUST NOT get Unknown either (REQ-93).

    Case Outcome
    The source has an equal value Match (code)
    The source has a different value NoMatch (code)
    The source does not know the BSN Unknown (code)
    The source has no value for this citizen, for example no residential address because he is not a resident Unknown (code)
    The source has an incomplete value: an address without street, house number, postal code, or town Unknown (code)
    An attribute that this data service does not deliver 404, and the ASIP does not ask the source (code)
    The source is unreachable, or the chain refuses 503 or 500, see REQ-93 (code)

    REQ-85: The verify response contains no value from the source¶

    On Match and MatchWithVariation, the ASIP MUST NOT return an attributeValue, and for fragments no fragmentValue. The QTSP only learns whether its value is correct.

    REQ-86: The access token carries the citizen's identification data and the means used to identify him¶

    The authorization server MUST issue access tokens as a JWT according to RFC 9068. Each token MUST be bound to a key of the QTSP and MUST carry the scope for each operation (verify, retrieve). The token MUST carry the identification data of the citizen as the identification means delivers them. It MUST always carry the BSN. Of the mandatory PID attributes, it MUST carry only those that the means delivers.

    The token MUST name the means in acr and amr. The authorization server MUST establish that means itself, and MUST NOT copy what the means declares. An identification without a BSN MUST NOT lead to a token. The BSN in the token MUST be readable only for the ASIP. A QTSP without BSN authority that holds the token MUST NOT be able to read it.

    Logged in with DigiD (mock) the BSN, with acr and amr set to digid-mock, and no PID attributes (code)
    A QTSP without BSN authority reads the token no readable BSN. This is a proposal. In the demo, the BSN in the token is readable.
    Logged in with the NL Wallet the BSN, family_name, given_name, birthdate, and nationalities, with acr and amr set to nl-wallet. No place of birth (F-94) (code).
    The means delivers no BSN no authorization code. The citizen sees the request page again, and the transaction stays (code).

    REQ-87: The ASIP takes the citizen only from a valid token bound to the QTSP that covers the operation¶

    On every verify and retrieve request, before any other check, the ASIP MUST validate the access token according to RFC 9068 §4 (signature with a key of the authorization server, issuer, audience, validity). It MUST validate the binding to the key of the QTSP with a valid DPoP proof for this request according to RFC 9449. It MUST check that the scope covers the operation. The identification data of the citizen MUST come from that token, never from the request. Every authentication or authorization error MUST be 401, with a WWW-Authenticate challenge. If the keys of the authorization server are not available, the ASIP MUST give 503.

    Case Outcome
    No token 401, challenge without an error code (code)
    Signature, issuer, audience, expiry, or typ is wrong, or the token has no cnf or no BSN 401 invalid_token (code)
    No proof 401 invalid_request (code)
    Proof invalid, reused, or with another key than cnf.jkt 401 invalid_dpop_proof (code)
    The scope does not cover the operation 401 insufficient_scope, with the scope in the challenge (code)
    The token names attributes and the request asks another attribute 401 insufficient_scope (REQ-103) (code)
    An invalid token and an invalid request 401: the token comes first (code)
    Keys of the authorization server not available 503 (code)
    • Status: ready for review
    Source, evidence and notes
    • Source: design:
      • ETSI TS 119 478 REQ-ASIP-6.1.1.2-12 (401 "due to an authentication or authorization error"). Implementing Regulation (EU) 2026/1735 designates clause 6.1.1.
      • ETSI REQ-ASIP-4.3-03 ("access controls … to determine that the requester is a trust service provider and is acting at the request of a legitimate user").

    If the source has no value for a requested attribute, the ASIP MUST answer a retrieve request with 404, with the attribute in the reason. A retrieve MUST NOT give a partial result: a 200 MUST contain every requested attribute. Verify still gives Unknown (REQ-84).

    Case Outcome
    The source has a value for every requested attribute 200 with every attribute, sealed (code)
    The source has no value for one attribute, also next to an attribute with a value 404 without a seal. The reason names the attribute (code).
    Attribute not in the catalogue of the data service 404 (REQ-94) (code)
    Verify, the source has no value Unknown (REQ-84) (code)
    • Status: ready for review
    Source, evidence and notes
    • Source: design. The source is ETSI TS 119 478 REQ-ASIP-6.1.2.2-06 ("404 … at least one of the requested attributes … was not found") and -02-01 ("one or more attribute objects"). GBO reads these requirements so that no value in the source also counts as not found.
    • Addressee: interface agreement: every ASIP. GBO-delivered component: the ASIP.
    • Evidence: PR #541, PR #542. Code and tests:
      • Historical code: service.go#L152-L158 and handler.go#L366-L367. The test for one and two attributes is in handler_test.go#L291-L319.
      • Code at v0.9.0: service.go#L198-L236 and handler.go#L375-L376. The test is in handler_test.go#L291-L315.

    • Notes: a missing value also tells something about the person, for example that he has no Dutch address. The citizen authorized the request himself (REQ-90).

    REQ-102: The authorization server identifies the citizen with the EUDI wallet through OpenID4VP and asks only the PID attributes in its registration¶

    The authorization server of the ASI MUST be able to identify the citizen with the EUDI wallet through OpenID4VP. It MUST act as a registered wallet relying party of its own, and ask only the PID attributes that are in its registration. The PID MUST come from a trusted PID issuer and contain a BSN. A presentation of another type, or without a BSN, MUST NOT lead to an identification.

    PID without BSN, another type, another query ID, or no presentation not identified (code)
    Return on the same device with the session of another browser, or without a valid nonce not identified (code)

    REQ-103: An authorization can be bound to the requested attributes, and the ASIP then processes only those attributes¶

    An authorization request can name the attributes that the QTSP wants to verify or retrieve. The authorization server of the ASI MUST then check that these attributes belong to exactly the data service and the operations of the request. It MUST refuse an invalid list, show the attributes to the citizen, and put them unchanged in the access token. If the token carries such a list, the ASIP MUST refuse a request that names an attribute outside the list.

    A policy under article 9(5) of Implementing Regulation 2025/1569 can make the list mandatory (Q-33). Without such a policy, the authorization server MUST treat a request without a list as an authorization per operation according to ETSI TS 119 478. The catalogue of the data service is then the limit.

    Case Outcome
    No list authorization per operation, a page without attributes, and a token without a list. The ASIP allows every attribute from the catalogue (code).
    No list, list made mandatory invalid_request (code)
    The list is empty, of an unknown type, or for another data service. Or the list has other operations than the scope, no attributes, or invalid or duplicate attributes. invalid_request (code)
    Valid list attributes on the page and unchanged in the token (code)
    Token with a list, and the request names another attribute 401 insufficient_scope. The reason names the attribute (code).
    • Status: draft
    Source, evidence and notes
    • Source: design:
      • Implementing Regulation (EU) 2025/1569 article 9(5). A member state can impose access control.

Without a binding, the QTSP can ask every attribute from the catalogue with the same token, also when the citizen approved something else.

    REQ-113: Fuzzy matching only on free text, with documented rules¶

    An ASIP that supports fuzzy matching (REQ-ASIP-6.1.1.1-10) MUST apply it only to free text, such as names and address lines. It MUST NOT apply it to dates, codes, and numbers. It MUST publish the rules that it applies. A QTSP then knows when it can get MatchWithVariation.

    Case Outcome
    A name that differs only in case, diacritics, hyphens, or white space MatchWithVariation (code)
    A date or code that differs only in this way, for example 1990-01-01 and 1990 01 01 NoMatch. For dates, the demo does this since v0.9.0 (code). For codes, see the notes.
    • Status: draft
    Source, evidence and notes
    • Source: design. The source is ETSI TS 119 478 REQ-ASIP-6.1.1.1-10. It leaves fuzzy matching free. It names differences in transliteration, spaces, hyphens, and compounding "and similar orthographic variations". These differences fit text and do not fit a date or a code. ETSI prescribes no rules, and this requirement makes that stricter.
    • Addressee: interface agreement: every ASIP that offers fuzzy matching.
    • Evidence: PR #499. Code and tests:
      • Historical code: the rules are documented (README asi-provider#L143) and built (match.go#L110-L131). The test is in handler_test.go#L119-L136. At that commit, the demo normalized every string (match.go#L44-L48).
      • Code at v0.9.0: since step 5 of ICTU/GBO-demo#592 (PR #624), a string with a format in the value schema matches exactly or not. An example is the birth date (match.go#L27-L54, asi-attributes.json). The rules are in the README asi-provider#L158. The test is in service_test.go#L330-L348.
    • Related: REQ-84, REQ-85, Q-38, Q-70 (normalization for each kind of value), ADR 0039.
    • Notes:
      • The value schema of an attribute marks what free text is. The source metadata define this (ICTU/GBO-demo#592: "fuzzy matching follows the type", through value_schema). In v0.9.0, the marker is the JSON Schema format.
      • The demo still normalizes a code without a format. Nationality nl against NL gives MatchWithVariation. A postal code in another way of writing also gives MatchWithVariation. For codes, demo v0.9.0 does not meet the requirement.
      • The rules of the demo itself (ICAO Doc 9303, diacritics, hyphens, white space, case) are not a requirement.

    REQ-115: The ASIP verifies attribute fragments¶

    The ASIP MUST support the verification of attribute fragments (REQ-ASIP-6.1.1.1-07, -08). The contract of every data service MUST describe which JSONPath expressions (RFC 9535) the ASIP accepts for a fragment.

    Case Outcome
    Fragment with an expression from the supported subset Match, MatchWithVariation, or NoMatch (code)
    Expression that selects nothing in the source value Unknown (code)
    Expression outside the subset 400 (code). There is no decision whether this must be 400 or 501.
    • Status: draft
    Source, evidence and notes
    • Source: design. ETSI TS 119 478 leaves fragments free (REQ-ASIP-6.1.1.1-08-01). If the ASIP does not support fragments, it gives 501 (REQ-ASIP-6.1.1.1-09). With fragments, a QTSP can have one part of an attribute verified without sending the rest. An example is the town of an address.
    • Addressee: GBO-delivered component: the ASIP. Interface agreement.
    • Evidence: ICTU/GBO-demo#608 is not built in demo v0.9.0. The built part comes from PR #499. Code and tests:
      • Historical code: the demo supports a subset of JSONPath (match.go#L149-L210, service.go#L211-L233). The tests are in handler_test.go#L169-L188 and service_test.go#L82-L87.
      • Code at v0.9.0: the subset is in match.go#L176-L187, and the fragment check is in service.go#L290-L317. The test is in handler_test.go#L165-L184.
      • The description in the contract is not built in demo v0.9.0. The subset is only in the README asi-provider#L160.
    • Related: REQ-112, REQ-113.
    • Notes:
      • The choice of subset is a choice for the contract and is no requirement.
      • The demo answers an expression outside its subset with 400 (service.go#L220-L221). There is no decision whether an expression that the ASIP does not support gives 400 or 501.
      • In v0.9.0, a fragment can point to a member that the source description does not provide, or provides as a constant. That fragment gets Unknown, and the ASIP does not ask the source (service.go#L140-L161).
