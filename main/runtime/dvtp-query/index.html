    DvTP: the consumer queries a source under consent¶

    A consumer (afnemer) asks a source for data about a citizen who gave consent. The consumer sends a GraphQL query and the consent proof through FSC. The PDP of the source decides before any data reaches the source. After an allow, the source fills in the citizen. Besides the direct call, the flow has two variants: a call by an integrator, and a call by the Installatie Register to LVG.

    For the concepts, see Authorization, Consent, and Pseudonymization. For the components, see Level 2: authorization chain and Level 2: bronhouder. The main decisions are ADR-0031, ADR-0032, and ADR-0033.

    The precondition is that the consumer has an FSC contract with the source. The Manager of the source signed the contract after a positive admission decision of the same PDP (REQ-61, REQ-62). For that scenario, see Admission and activation.

    Data per hop¶

    The tags (for example Medium and Low) are the data classes of What travels where. The hop numbers refer to the steps of the sequence:

    # From → to Endpoint In Out Data and notes
    1 Consumer backend → HV Outway POST /bri/graphql Body {query, variables} with variables.bsn = "consent:identity". Headers X-GBO-Consent-Token, Fsc-Transaction-Id, and traceparent — Plain GraphQL, no envelope. The placeholder names the citizen (REQ-79). The consumer reads only consent_id and scopes from the proof (token.go#L32-L52). It sends the proof unchanged (AV-05, outway.go#L34-L51). The year filter travels inside the query (kind.go#L75-L95)
    2 HV Outway → BD Manager Token request Grant hash of the bri contract — The Manager of the providing peer issues the access token
    3 BD Manager → HV Outway — — Access token (certificate-bound JWT) Medium. The token carries sub, service_name, grant_hash, and service_peer_id. It has no grant properties, so flow and subject_id_type are not in it (REQ-74)
    4 HV Outway → BD Inway FSC transport Body 1:1, Fsc-Authorization, X-GBO-Consent-Token, and Fsc-Transaction-Id — FSC native transport over mTLS (ADR-0003)
    5 BD Inway → PDP POST /authzen/v1/evaluation subject (HV peer, token attributes), action.properties.body, resource, and context.headers — The AuthZEN plugin of the Inway is the PEP. It passes the request unchanged (REQ-42). The Inway sends no traceparent. It correlates with X-Request-ID = Fsc-Transaction-Id (ftv-graphql-profile.md#L105-L106)
    6 PDP (internal) Mapper, then policy AuthZEN request FTV field list The mapper only maps (Query mapping). The policy reads the token from the headers and selects the regime (engine.rego#L173-L181, Regime selection)
    7 PDP → register GET /.well-known/jwks.json — — Direct, without FSC. Only if the cache is empty or older than 300 seconds, or if the kid is unknown
    8 Register → PDP — — ES256 public keys Low. No stale-key fallback
    9 PDP (internal) Proof verification X-GBO-Consent-Token consent_id, scopes, dienstverlener_oin, and valid_until The policy verifies the proof. The mapper does not (REQ-68, REQ-18, consent.rego#L174-L186). The policy does not read encrypted_subject. It only requires a pseudonym per party
    10 PDP → PDP Outway GET /consent-status/consents/{id}/status consent_id, traceparent, and Fsc-Transaction-Id — Medium: consent_id. Per evaluation, no cache, 2-second timeout, and raise_error: false (consent.rego#L194-L200)
    11 PDP Outway → Register Inway FSC service consent-status Same as hop 10 — From the PDP peer …0800 to the register peer …0700 (FSC peers, REQ-76)
    12 Register Inway → register Status listener, port 4012 consent_id — The listener serves only the status. If the request has no FSC peer, the listener answers 401. The register logs the lookup with the calling peer as processor
    13 Register → PDP — — {status} or 404 Only the status is online. The content of the consent comes from the proof (F-61)
    14 PDP (internal) Rules Resolved consent, field list, and subject Decision per field DVT0001 binds the fields of service bri. It checks actor binding, placeholder, scope, years, and fields (REQ-48, REQ-97, dvt0001.rego#L72-L80). The PDP input holds no BSN and no pseudonym
    15 PDP → BD Inway AuthZEN decision — decision: true, granted fields The engine adds the resolved consent to its response for the console log (engine.rego#L25-L29). The ADL records the request and the decision (ADR-0036)
    16 BD Inway → bron-sidecar POST /graphql Body 1:1, X-GBO-Consent-Token, and Fsc-Authorization — The Inway forwards only after the allow. Only the source Inways reach the source gateway (REQ-81, Network isolation)
    17 Source gateway (internal) Substitution Proof, body VI for OWN_PEER_OIN If the request carries a consent token, the source gateway takes the subject from that token. The source gateway does not verify the token again (substitution.go#L105-L107)
    18 Source gateway → decryption component POST /signed-encrypted-identity VI, own decryption keys, and scheme keys — For consent:pseudonym, the source gateway sends the VP to /signed-encrypted-pseudonym. No BSNk call in the query path (REQ-21, BSNK-09)
    19 Decryption component → source gateway — — BSN, recipient OIN BSN, inside the source boundary. In the demo, the three sources share one decryption component and one OIN
    20 Source gateway (internal) Recipient check and substitution BSN, recipient Body with the BSN The value must name the own OIN as recipient (REQ-80, substitution.go#L213-L232). The source gateway logs the decryption in the LDV logbook of the source
    21 Source gateway → source POST /graphql variables.bsn = BSN — BSN only at the source. The query and operationName stay the same
    22 Source → source gateway — — {data} Only the selected fields (REQ-08). The source gateway logs the forward
    23 to 25 Source gateway → BD Inway → HV Outway → consumer — — {data} No BSN in the response. The consumer logs its processing under the consent_id (F-76, Q-27)

    Variant: an integrator calls for the consumer¶

    An integrator is a software party that calls the source for a consumer under FSC delegation (ADR-0034, integrator.md). The demo runs this variant opt-in with make demo-integrator. The consent stays a consent to the consumer (Hypotheek-BV, peer …0300).

    sequenceDiagram autonumber box rgb(241,239,232) Integrator participant INT as integrator-backend end box rgb(220,252,231) GBO Basis participant IO as Integrator Outway participant BDM as BD Manager participant BDI as BD Inway (PEP) participant PDP as OpenFTV PDP end box rgb(237,233,254) Admission register participant REG as Admission register end REG-->>PDP: acts_for of the integrator (PIP pull, every 5 s) INT->>IO: POST /bri/graphql with the proof of Hypotheek-BV IO->>BDM: Request an access token for the delegated grant BDM-->>IO: Access token, sub = integrator, act.sub = Hypotheek-BV IO->>BDI: Body, headers and token BDI->>PDP: AuthZEN, subject.id = integrator,<br/>outway_delegator_peer_id = Hypotheek-BV PDP->>PDP: Proof names Hypotheek-BV?<br/>Integrator active and mandated for Hypotheek-BV in DVT0001? PDP-->>BDI: Allow or deny Note over BDI: After an allow, hops 16 to 25 of the main sequence follow

    The integrator variant differs from the direct call in these hops:

    # What differs from the direct call
    1 The admission register (dvtp-onboarding-register) supplies integrations as acts_for on the entry of the integrator. A mandate names the represented party and the rules (REQ-106, AV-06)
    2 integrator-backend is the consumer backend behind the own Outway of the integrator (peer …1100). The proof is the proof that the portal gave to Hypotheek-BV
    3 to 4 The contract is a DelegatedServiceConnectionGrant between the integrator, Hypotheek-BV, and the source. The OpenFSC Manager puts the delegator in act.sub. This is the reverse of RFC 8693 (integrator.md#L61-L67)
    6 The Inway maps the delegator to subject.attributes.outway_delegator_peer_id. The policy reads that field and does not read the claim
    7 The consent binds the represented party. This is the delegator, or else subject.id (lib.rego#L62-L72). Every delegated call also needs a mandate for that party and the granting rule (engine.rego#L253-L266)

    At the source, the source gateway and the source log the integrator as foreignOperation.processor. The LDV record has no field for "on behalf of". The FSC transaction log of the source records both peers (integrator.md#L132-L152). It is open whether the proof must name the integrator (Q-46).

    Variant: the Installatie Register asks LVG about ownership¶

    The LVG pilot uses the same consent pattern with a different consumer and a different source (lvg-ir.md). The Installatie Register (IR) asks the national buildings facility (LVG) whether a building unit belongs to the citizen. The citizen gives two consents:

    • One consent to IR in the consent portal (toestemmingsportaal), with scope lvg:vbo:eigendom. This consent is in GBO.
    • One consent to the installer inside IR. This consent is not in GBO.
    sequenceDiagram autonumber box rgb(221,235,247) Citizen actor B as Citizen end box rgb(241,239,232) IR participant K as keyper-mock (IR) participant IRB as ir-backend end box rgb(220,252,231) GBO Basis participant IRO as IR Outway participant BDI as BD Inway (PEP) participant PDP as OpenFTV PDP participant LS as lvg-sidecar end box rgb(221,235,247) Source participant LVG as lvg-graphql-server end Note over K: Holds the proof of the consent<br/>citizen to IR, scope lvg:vbo:eigendom B->>K: Approve the installer (IR consent, outside GBO) K->>IRB: Ownership check for a vboId, with the proof IRB->>IRO: POST /lvg/graphql<br/>vbo(bsn = consent:identity, vboId) IRO->>BDI: FSC, service lvg on peer …0200 BDI->>PDP: AuthZEN evaluation PDP->>PDP: LVG0001 with the consent checks of DVT0001,<br/>scope pinned to lvg:vbo:eigendom PDP-->>BDI: Allow BDI->>LS: Body and proof unchanged LS->>LS: Decrypt the VI, replace the placeholder with the BSN LS->>LVG: vbo(bsn, vboId) LVG-->>IRB: vboId or null, back through LS, BDI and IRO IRB-->>K: Ownership confirmed or not

    The LVG variant differs from the direct call in these hops:

    # What differs from the direct call
    2 to 3 ir-backend is the consumer backend with QUERY_KIND=lvg (kind.go#L47-L53). The query is vbo(bsn: $bsn, vboId: $vboId) { vboId } with the placeholder in $bsn
    4 IR has its own peer …1000, so the actor binding tells IR apart from Hypotheek-BV. LVG is a logical source behind bd-inway on the shared provider peer
    5 to 6 Hops 6 to 14 of the main sequence apply: proof verification and the online status lookup. If a consent does not have the LVG scope, LVG0001 denies with SCOPE_NOT_ALLOWED
    9 lvg-sidecar logs lvg-identiteit-ontsleuteling and lvg-bronquery-doorgifte in the LVG logbook. lvg-graphql-server logs lvg-vbo-eigendom, also for null
    11 to 12 Three outcomes are possible: the vboId (the citizen is the owner), null (not the owner), or a deny (no valid consent). Only if the citizen is the owner does IR record the access of the installer (lvg-ir.md#L64-L70)

    IR keeps the proof. At every access of an installer, IR asks again under the same consent. After a revocation, the next question fails (lvg-ir.md#L60-L62, Repeated use). With one consent, IR can ask about any vboId. The pilot must answer whether the vboId belongs in the consent (lvg-ir.md#L113-L114).

    Error paths¶

    A deny carries two layers of reason (Reason codes, REQ-06):

    • Consumer code: the PDP puts this code in reason_user, and the ADL stores it. It never names the field or the failed check.
    • Administrator codes: these codes are per field. They reach only the OPA console decision log. For a server fault, the request code is PIP_UNAVAILABLE, and the trace keeps the cause.

    In demo v0.9.0, the FSC Inway removes the consumer code. The Inway reads reasonUser, but the PDP sends reason_user (ftv-graphql-profile.md#L93-L96). As a result, the consumer gets a deny without a code. The consumer backend then shows UNAVAILABLE to the citizen (denial.go#L12-L56).

    On every PDP deny, no request reaches the source gateway or the source. If one field has more than one reason, the administrator code is the first reason in a fixed order (engine.rego#L321-L339). The error paths have these triggers and codes:

    Observations¶

    The DvTP run in demo v0.9.0 shows these facts:

    • The evidence selects the regime. A consent token, verified or not, puts the request in the consent regime. If the request has no consent token, only PID-regime rules apply. No header, grant property, or default decides the regime (REQ-74, ADR-0031). The PID regime starts when a proof is absent. As a result, its actor lists must stay disjoint from consent consumers (F-70).
    • The legal basis travels as a proof, and the status stays online. The PDP verifies the proof locally. It asks only for the status, per request and fail-closed (REQ-68, F-61). As a result, every DvTP request depends on the register (REQ-75, Q-05). The status answer is not in the PDP input, so the ADL cannot replay the decision (F-72).
    • The subject comes from the proof. The consumer names the citizen only with a placeholder (REQ-79, Subject binding). The PDP does not check who the subject is. It checks only that the subject comes from the proof. One request is about one citizen (F-77).
    • The rule "after the decision" depends on network isolation. The source gateway does not verify the token again. A consumer holds real proofs, so a second verification gives no protection. Only the source Inways reach the source gateway (REQ-81, F-79, ADR-0033). In Kubernetes, this isolation needs a NetworkPolicy (Deployment units and network zones).
    • BSNk is not in the query path. The source reads its own value with its own keys (REQ-21, BSNK-04). A source keeps older keys while proofs for that key version are valid (AV-09). In demo v0.9.0, no demo rule accepts consent:pseudonym, because no demo source takes a pseudonym (#474).
    • The PDP gives a clean deny instead of an HTTP error. For an unknown consent or an unreachable register, the PDP makes a policy decision with a reason in the decision record. The consumer does not get an upstream error (F-24).
    • The records correlate. The consumer sends traceparent and Fsc-Transaction-Id (REQ-55, AV-01, ADR-0035). The Inway does not pass traceparent to the PDP. The policy puts both on the status lookup. For how the records join, see Logging.
    • A suspended consumer keeps access. A consumer with an existing contract can still send queries, also with a valid consent (REQ-110, Q-53).
